# M3 正式业务行为规格

日期：2026-10-19。已随执行契约获用户批准；SHALL/MUST 表示验收义务，不表示已实现。实际状态与证据见 ../execution-plan.md。

## ADDED Requirements

### Requirement: M3-01 正式身份与内置网关

系统 SHALL 以最新 CurrentUser、同一 AsyncSession 和显式确认上下文执行 builtin 能力；租户、操作者、组织、权限和席位从服务端复核，不信任模型或请求体的同名字段。未实现能力 MUST 明确拒绝且不回退 Mock；直接服务、工具、图恢复及 API 适用相同边界。

#### Scenario: 授权在确认后失效

WHEN 用户确认后被禁用、转部门或撤销权限，THEN 写入和幂等重放均先重新授权，不能因历史确认或图状态继续执行。

### Requirement: M3-02 核心桥接与只读对账

系统 SHALL 实现以下 13 项核心映射及两个辅助读能力。写命令 MUST 绑定操作者、业务版本和规范化载荷；同键异载荷冲突，同键同载荷返回原结果。结果查询只读，不能重发命令；未找到结果不等同业务失败，也不触发自动补写。

| 编号 | 契约 / 对应既有外桥路径 | builtin 权威与边界 |
| --- | --- | --- |
| C01 | capabilities / GET /capabilities | 实际可用能力；不含敏感配置 |
| C02 | get_user_context / GET /users/{id} | 最新正式身份；仅当前人或明确组织读范围 |
| C03 | get_leave_case / GET /leaves/{id} | 正式请假与授权版本；无旧单据回退 |
| C04 | get_leave_balance / GET /users/{id}/leave-balance/{type} | M2 账户/台账；跨年明细，禁止浮点裁决 |
| C05 | get_approval_route / GET /leaves/{id}/approval-route | 已发布模板和组织解析，仅建议快照 |
| C06 | create_or_update_approval / POST /approvals | 正式提交或当前审批命令；忽略外部自拟路线，拒绝歧义动作 |
| C07 | get_approval_result / GET /approvals/results/{key} | 授权读取既有命令结果 |
| C08 | edit_leave_case / POST /leaves/{id}/edit | 正式可编辑草稿和 expected revision；在审关键字段按 M2 退回重提 |
| C09 | get_leave_edit_result / GET /leaves/edits/{key} | 授权读取既有修改结果 |
| C10 | create_or_merge_ticket / POST /tickets | 正式工单与确认、版本、分派规则 |
| C11 | get_ticket_result / GET /tickets/results/{key} | 新增缺失的工单写入对账 |
| C12 | notify / POST /notifications | 只保存获授权的通知意图；受理不等于送达 |
| C13 | get_notification_result / GET /notifications/{key} | 持久化通知及渠道尝试状态 |
| A01 | get_ticket_status | 明确类型的辅助读，按正式工单权限 |
| A02 | get_field_dict | 明确类型的辅助读，仅返回授权可用的已发布字段/规则版本 |

原协议 11 个方法，原 HTTP 文档 12 条（包含 capabilities）；C11 是新增项。builtin 不需要自调用 HTTP。real 新增能力不具备时拒绝该能力，不能用空成功或 Mock 补齐。

#### Scenario: 写入后进程退出

WHEN 业务已提交但图未保存检查点，THEN 以原业务键只读核验结果；恢复后同键只产生一次领域动作和审计，权限不足则拒绝披露。

### Requirement: M3-03 共用流程与版本保持

系统 SHALL 在共用流程实例中区分 leave/reimbursement，每个实例必须且只能关联一个相符的业务版本；模板、字段字典、路由、表单及规则快照固定。M2 历史实例、余额及日期行为 MUST 保持；未知字段、任意表达式、跨场景条件和未发布模板拒绝。

#### Scenario: 模板发布后存在在办申请

WHEN 管理员发布新金额阈值或字段规则，THEN 只影响新提交版本，已有实例不被覆盖；非法业务版本组合在数据库和服务层均拒绝。

### Requirement: M3-04 报销金额和生命周期

系统 SHALL 支持人民币报销草稿、提交、单签/会签/或签、驳回重提、撤回、归档和转交恢复。金额以十进制字符串输入、整数分存储，必须大于零且至多两位小数，上限 999999999.99；不得静默舍入、接受非数值或浮点分支。金额路由按发布版本的有序条件和默认分支裁决。批准 MUST 不触发付款。

#### Scenario: 金额路由临界值

WHEN 阈值为 1000.00，分别提交 999.99、1000.00、1000.01，THEN 路线符合所配置的 lt/le/eq/ge/gt；0、负数、三位小数、无穷值、越界值均拒绝。

### Requirement: M3-05 发票与私有附件

系统 SHALL 要求报销提交含至少一张本单据的发票附件；仅 PDF/PNG/JPEG、通过扫描且完整性校验成功的不可变文件可提交。上传、预览、下载和历史版本引用 MUST 受最新业务权限约束；未配置扫描不得视为 CLEAN。

#### Scenario: 引用他人的发票

WHEN 申请人使用其他报销单、请假单或其他租户的文件 ID，THEN 提交拒绝；文件丢失、替换、待扫描和扫描失败也拒绝。

### Requirement: M3-06 正式工单闭环

系统 SHALL 支持人工草稿确认创建、本人重复候选确认合并、规则分派、授权人员领取/改派/状态办理、申请人反馈和负面反馈重开。正式工单不得由旧 Mock 工单充当权威；无规则进入待领取。合并目标及目标 revision MUST 纳入幂等载荷，确认后目标变化必须重新确认；并发领取仅一人成功。

#### Scenario: 同键更换合并目标

WHEN 用户用同一操作键从合并 A 改为合并 B，THEN 冲突且不修改任一目标；重复原命令返回原结果。非本人合并、越部门分派及非有效成员办理拒绝。

### Requirement: M3-07 站内信与 SMTP

系统 SHALL 持久化通知意图、收件箱、每渠道任务和每次尝试；支持 PENDING/PROCESSING/ACCEPTED/FAILED/UNKNOWN/CANCELLED 及下次尝试、租约和稳定消息 ID。站内唯一入箱和已读应幂等；SMTP ACCEPTED 仅代表服务器受理。明确未受理的暂时失败有限重试，永久失败停止，结果不明 MUST 进入 UNKNOWN 待核对，不盲目重发。

#### Scenario: SMTP 受理后失去响应

WHEN SMTP 可能已接收但连接或进程中断，THEN 状态为 UNKNOWN 或经恢复转 UNKNOWN，不能宣称失败后安全自动重发；批准的业务状态保持成功。

### Requirement: M3-08 通知和定时器当前权限

系统 SHALL 在入箱、发送和读取时复核收件人、来源权限及有效业务状态；提醒仅适用当前有效节点，终态取消未发提醒，重复扫描不重复入箱或推进业务。SMTP 正文 MUST 仅含非敏感提示和登录入口；不放申请理由、发票、合同或问答全文。收件邮箱须由授权用户/管理员配置，不从模型提取。

#### Scenario: 排队后终态或调岗

WHEN 提醒排队后流程结束或收件人失权，THEN 未发提醒取消、敏感详情不披露；曾受理消息保留事实记录，不伪造撤回邮件。

### Requirement: M3-09 原子命令和脱敏审计

所有正式写入 MUST 与命令结果、业务审计及待发送事件同事务；记录操作者、对象/版本、脱敏前后变化、时间、操作键和追踪 ID。审计/outbox 失败必须回滚业务；口令、令牌、SMTP 凭据和私密正文不得进入日志、图追踪或普通审计。

#### Scenario: 通知投递失败

WHEN 业务事务提交后 SMTP 失败，THEN 保留批准/工单结果，只改变投递记录；业务事务内审计失败则整个领域动作回滚。

### Requirement: M3-10 智能意图与人工确认

系统 SHALL 保留意图识别、澄清、工具白名单与路由审计；未知转人工。AI 仅提供解释和修改建议，确定性代码裁决额度、重叠、路由、附件和金额。写确认 MUST 由服务端绑定用户、线程、动作、对象/节点版本、规范化载荷及有效期；图状态或模型自报 confirmed 无权替代。

#### Scenario: 确认后节点变化

WHEN 或签被其他人完成或草稿被编辑，THEN 原确认失效；再次操作需要展示最新内容并确认，不能用旧路线或旧批准人覆盖正式流程。

### Requirement: M3-11 知识来源与输入边界

系统 SHALL 先按租户、最新部门权限、有效发布版本过滤再检索，生成前重新核对引用；来源不足、版本变化或失权转人工。正式知识不得回退旧无权属 chunk。文档/邮件内容 MUST 仅作为数据，不得改写策略或工具权限；模型输入和工具输出限量脱敏。

#### Scenario: 检索后来源撤回

WHEN 命中知识在生成前下架、改版或撤销权限，THEN 不继续引用旧正文；嵌入检索和关键词检索均不得跨范围补齐。

### Requirement: M3-12 P2/P3 与正式管理边界

系统 SHALL 对文档、邮件、会议、工作任务、报表、合同及其导出/预览/引用逐一验证最新 self/department 权限；报表读取正式工单/审批且不混用旧 Mock 数据。知识、策略、审计、运行管理仅在完成各自正式范围过滤后开放，不得一次性移除全部 503。通知和人工业务不依赖 AI 开关；模型不可用返回可理解的人工处理路径。

#### Scenario: 部门报表和来源权限不同

WHEN 用户有报表权限但没有某个来源工单/审批权限，THEN 查询、聚合、缓存、导出均排除该来源；更改权限后历史结果重新校验且不能泄漏汇总。

### Requirement: M3-13 人工工作台与中文界面

系统 SHALL 提供报销、工单、审批与站内消息的人工操作页面，使用结构化表单和中文业务文案；AI 关闭仍可办理。金额、版本冲突、扫描、队列和 UNKNOWN 状态须清楚展示，失败不得显示为成功；并发点击、移动端和刷新恢复不能重复提交或丢失本地编辑。

#### Scenario: 手机办理报销

WHEN 用户在 390px 页面上传发票、保存、提交并查看驳回原因，THEN 操作可见、内容不遮挡；失权后直达地址与既有页面均拒绝越权。

### Requirement: M3-14 隔离验证与可复现证据

系统 MUST 仅在获本阶段批准的专用测试/预览库运行迁移和重置，显式核对三个数据库地址及安全校验；Mock 模型/嵌入和本机 SMTP 测试服务。保留原库、真实配置及旧预览。每批 SHALL 保存真实测试和实施者复核记录，覆盖迁移、权限、并发、恢复、旧功能和桌面/手机；未运行与限制如实列出。

#### Scenario: 误用开发库

WHEN 测试继承了开发 .env 或目标地址不在批准列表，THEN 在任何迁移或清表前中止；不得通过默认变量、随机额外建库绕过范围。
