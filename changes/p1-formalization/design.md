# P1 正式化升级架构设计

## Context

当前系统是一个可运行的 MVP：Vue 前端直接调用 FastAPI，FastAPI 通过 LangGraph 编排请假、FAQ 和工单子图，并以 PostgreSQL 保存会话、消息、预检、人工决定、知识和审计数据。`MockAdapter` 同时承担 OA 权威数据和写入模拟，`RealOAAdapter` 尚未实现；应用启动依赖 SQLAlchemy `create_all` 建表。

正式化升级必须同时满足两个产品形态：

1. 没有外部 OA 时，系统以内置数据库完成请假、逐级审批和工单闭环。
2. 企业已有 OA 时，系统保留智能编排、交互和审计能力，由适配器读取并写回外部权威系统。

约束如下：

- 仅交付正式 PRD P1，不包含会议、文档、邮件、合同、报表或通用任务管理。
- 不自建企业 SSO、完整组织人事主数据或通用 BPMN 引擎，只定义认证与组织权限适配契约。
- 高影响操作必须经过人工确认；LLM 不决定权限、审批人或最终业务状态。
- 现有 MVP 数据和演示流程需要兼容迁移，不能通过重建数据库解决升级问题。
- 新功能按批次开工前向用户报备；设计批准不等于批准实现所有批次。

### Stakeholders

| 角色 | 关注点 |
| --- | --- |
| 员工 | 能填写、修改、追踪申请和工单，刷新或重启后继续处理 |
| 审批人 | 只处理当前属于自己的节点，材料、风险和历史决定完整 |
| 客服 | 收到完整人工交接包，能分派、合并、处理和回写工单 |
| 管理员/知识运营 | 策略、灰度、知识版本和降级操作可控可回滚 |
| 审计/运维 | 可追溯业务与运行轨迹，敏感信息受控，故障可定位 |
| 集成开发者 | 内置、Mock、真实 OA 遵守同一能力与错误契约 |

## Goals

1. 建立可独立运行、可接外部 OA 的统一 P1 领域核心。
2. 将请假审批改为严格的版本化申请与逐级节点状态机。
3. 将会话、任务、人工接管、工单和知识治理从浏览器演示状态升级为服务端正式状态。
4. 对所有资源执行实时权限复核，对所有写入执行幂等和人工确认约束。
5. 打通业务审计与运行轨迹，同时控制敏感字段和导出权限。
6. 通过版本迁移、独立测试库、契约测试和恢复演练达到可上线工程标准。

## Non-Goals

- 不实现任意业务类型可视化拖拽流程设计器。
- 不在本系统维护企业员工主档、汇报关系或组织生命周期。
- 不为未知商业 OA 猜测私有接口；真实适配使用配置化通用 HTTP 契约并通过沙箱验证。
- 不把 LangGraph Checkpoint、审计日志或浏览器缓存作为业务权威库。
- 不在本阶段引入独立消息中间件、数据仓库或第三方可观测平台作为强制依赖。

## Architecture Overview

```text
Vue 工作台
  │  用户/审批人/客服/管理员/审计运维入口
  ▼
FastAPI 应用层
  ├─ 身份与资源授权
  ├─ 会话/任务 API
  ├─ 请假/审批 API
  ├─ 人工队列/工单 API
  └─ 知识/策略/审计/观测 API
  │
  ▼
P1 领域服务（唯一业务规则实现）
  ├─ TaskService / RoutingService
  ├─ LeaveService / ApprovalService
  ├─ SupportService / TicketService
  ├─ KnowledgeService / PolicyService
  └─ AuditService / RuntimeTraceService
  │                     │
  │                     └─ LangGraph：理解、编排、暂停与恢复
  ▼
ProviderBundle 能力端口
  ├─ builtin：PostgreSQL 权威实体
  ├─ mock：开发演示数据
  └─ real：外部 OA HTTP/认证/通知/工单适配
  │
  ▼
PostgreSQL + 文件存储接口 + 外部 OA
```

业务服务先完成授权与确定性校验，再决定是否调用 LangGraph。LangGraph 只保存和恢复编排位置，不直接绕过领域服务写业务表。所有适配器返回统一领域 DTO 和结构化错误。

## Decisions

### Decision 1：采用能力端口和 ProviderBundle，不维护两套业务流程

**Choice**

将当前单体 `OAAdapter` 拆成异步能力端口：

- `IdentityProvider`：用户、租户、角色、部门和数据范围。
- `LeaveProvider`：请假单快照、余额和时间冲突数据。
- `ApprovalProvider`：路由建议、审批实例创建、节点决定和状态对账。
- `TicketProvider`：创建、重复候选、合并、分派、状态与反馈回写。
- `NotificationProvider`：站内或 OA 渠道通知。

`ProviderBundle` 按环境选择 `builtin`、`mock` 或 `real` 实现，并声明能力集合。现有 `OAAdapter` 在兼容期作为 facade 转调这些端口。

**Rationale**

不同企业可能只接入部分外部能力。能力端口允许例如身份来自 SSO、请假和审批来自外部 OA、工单仍使用内置模块，而不复制业务规则。异步接口也避免当前同步适配器在 FastAPI 事件循环中阻塞。

**Alternatives considered**

- 保留一个不断扩大的 `OAAdapter`：改动较小，但能力缺失只能在运行时失败，难以部分接入和独立契约测试。
- 内置和外部 OA 分别实现业务服务：短期直观，但状态、权限和验收行为很快分叉，不采用。

### Decision 2：业务权威状态与编排状态分离

**Choice**

请假申请、审批节点、工单和人工队列使用普通关系表作为业务权威；`agent_thread` 作为任务索引和运行摘要；LangGraph Checkpoint 只保存编排上下文与恢复位置。每次恢复或产生写副作用前，领域服务重新读取权威状态。

**Rationale**

Checkpoint 适合图恢复，不适合列表查询、逐级审批并发控制、业务报表或外部 OA 对账。清晰分离可避免“图认为已批准、业务系统仍等待”的隐式不一致。

**Alternatives considered**

- 将完整业务对象存入 LangGraph state：实现快，但查询、迁移、并发和外部对账困难。
- 仅以外部 OA 为权威：无法满足已确认的内置完整产品模式。

### Decision 3：请假采用申请版本 + 审批实例 + 有序节点模型

**Choice**

新增下列领域实体：

| 实体 | 关键职责 |
| --- | --- |
| `leave_application` | 稳定业务号、申请人、当前版本、总体状态和权威提供方 |
| `leave_application_version` | 不可覆盖的表单快照、规则版本、提交人和版本号 |
| `leave_attachment` | 文件元数据、哈希、大小、类型、存储引用和安全扫描状态 |
| `approval_instance` | 对应某申请版本的审批实例、外部流程号和总体状态 |
| `approval_node` | 顺序、节点类型、审批人/角色、状态、截止时间和升级关系 |
| `approval_decision` | 节点决定、操作者、意见、编辑差异、幂等键和决定时间 |

同一审批实例最多一个 `ACTIVE` 节点。批准当前节点后激活下一节点；只有最后节点批准才完成实例。驳回结束当前实例，员工修改产生新申请版本并重新预检、重新建审批实例。`edit` 决定必须保存字段差异，并由规则判断继续流转或返回预检。

**Rationale**

当前单个 `human_decision` 不能表达多级节点、越级保护、版本差异或节点级催办。显式模型让约束可以在数据库事务与唯一索引中执行，而不依赖页面判断。

**Alternatives considered**

- 在 `agent_thread` JSON 中保存审批链：迁移简单，但并发审批、查询和审计无法可靠约束。
- 本阶段引入通用 BPMN 引擎：能力过重且超出 P1 单据范围，不采用。

### Decision 4：状态机由领域服务执行，数据库约束防止越级与重复

**Choice**

主要状态如下：

```text
申请：DRAFT → PRECHECK → NEEDS_FIX ─┐
                  │                 │ 修改新版本
                  └→ SUBMITTED ←────┘
                        │
审批：              ACTIVE → APPROVED → COMPLETED
                        ├→ REJECTED → NEEDS_FIX
                        └→ PAUSED → ACTIVE / MANUAL

节点：PENDING → ACTIVE → APPROVED / REJECTED
                 └→ ESCALATED → APPROVED / REJECTED
```

决定提交使用条件更新或行锁验证：实例版本、当前节点、节点状态、操作者授权和幂等键必须同时匹配。唯一约束保证一个实例只有一个活动节点，一个幂等键只对应一个载荷哈希。

**Rationale**

前端禁用按钮不能阻止并发或恶意请求。事务内状态校验可阻止两名审批人同时推进、旧页面重复决定和二级审批人越级操作。

**Alternatives considered**

- 只依赖 LangGraph interrupt ID：它能暂停流程，但不能完整表达业务节点授权与外部状态对账。
- 全局分布式锁：当前 PostgreSQL 单主库场景下不必要，行级并发控制更简单。

### Decision 5：会话与任务使用服务端投影，localStorage 仅保存界面偏好

**Choice**

保留 `agent_thread`，扩展结构化字段或关联投影以返回：任务标题、场景、状态、当前步骤、责任人、业务号、暂停原因、可用操作和最近活动时间。新增：

- `GET /api/agent/threads`：历史会话分页列表。
- `GET /api/tasks`：当前任务分页、角色视图和状态筛选。
- `GET /api/tasks/{id}`：统一任务摘要及目标详情链接。

Pinia 继续缓存最后打开项和筛选偏好，但页面初始化以服务端结果为准。

**Rationale**

用户跨页面、换浏览器和服务重启都需要恢复；浏览器缓存不能提供权限隔离、多人协作或历史列表。

**Alternatives considered**

- 继续将当前任务存在 localStorage：无法满足正式恢复要求。
- 为每个业务模块做独立任务列表：会导致状态含义和导航行为不一致。

### Decision 6：权限使用“认证事实 + 资源策略 + 调用时复核”三层模型

**Choice**

1. 认证适配器提供签名验证后的用户、租户、角色和组织声明。
2. 资源授权服务判断线程、申请、审批节点、人工项、工单、知识和审计数据范围。
3. 每次工具调用和高影响写入前重新调用授权服务；外部提供方可要求实时刷新组织/角色。

工具策略以 `(scene, role, scope, policy_version)` 生成动态允许集。拒绝结果只返回通用资源拒绝，详细原因写入受控审计。生产环境配置为 Mock 认证时就绪检查失败。

**Rationale**

角色菜单只解决可见性，不能替代后端资源授权。调用时复核可处理会话期间权限被撤销的情况。

**Alternatives considered**

- 只信任 JWT 中的长时效角色：无法满足动态撤权。
- 每个路由手写角色判断：容易遗漏资源范围且不可统一测试。

### Decision 7：所有副作用通过统一命令总线和幂等记录

**Choice**

业务写入包装为 `CommandEnvelope`：

```text
command_id / idempotency_key / actor / tenant / resource
payload_hash / trace_id / policy_version / created_at
```

`idempotency_record` 保存命令作用域、载荷哈希、执行状态、结果摘要和外部请求号。相同键同载荷返回既有结果；相同键不同载荷返回冲突。外部写响应不确定时保持 `UNKNOWN`，先按同一键对账再重试。

**Rationale**

请假提交、审批决定、通知、工单创建/合并、反馈和导出都可能因网络或客户端重试重复执行，需要统一机制而非各接口自行处理。

**Alternatives considered**

- 只使用业务号幂等：一个业务号包含多个合法动作，粒度不足。
- 仅依赖外部 OA 幂等：内置模式和本地审计仍可能重复。

### Decision 8：人工接管是正式领域对象，不是字符串状态

**Choice**

新增 `human_queue_item` 和不可覆盖的 `handoff_snapshot`。队列项包含来源任务、原因、优先级、队列、受理人、SLA、状态和结果；快照包含消息摘要、已采集字段、检索来源、工具结果、业务引用和权限标签。快照不复制不必要的敏感原文，客服读取时再次做资源授权。

**Rationale**

仅将 `next_action` 设置为 `human` 无法让客服发现、接管或回写，也无法衡量转人工率和 SLA。

**Alternatives considered**

- 自动创建普通工单作为所有人工接管：实现简单，但审批异常、知识复核和工单本身的人工处理语义不同。

### Decision 9：工单上下文与权威工单分离

**Choice**

当前 `ticket_context` 保留为智能层上下文投影，新增或由 Provider 提供权威 `TicketRecord`。草稿在确认前仅保存在会话/草稿实体；创建、合并、分派和反馈均通过 `TicketProvider`。内置 Provider 使用本地工单表，真实 Provider 保存外部工单号并定期或按需对账。

重复候选只给建议，合并需要用户或客服确认。负反馈创建复盘队列项，并通过同一幂等记录避免重复。

**Rationale**

智能抽取字段会多次修改，不应在用户确认前污染权威工单。上下文投影也允许外部 OA 工单字段与本地交互信息解耦。

**Alternatives considered**

- 直接扩展 `ticket_context` 作为所有模式的权威工单：外部系统接入时会出现双主写冲突。

### Decision 10：知识采用来源、版本、文件和切片四层模型

**Choice**

将当前一表一文档模型演进为：

- `knowledge_source`：稳定来源 ID、名称、类型和默认责任人。
- `knowledge_version`：递增版本、状态、生失效时间、权限标签、文件哈希和解析状态。
- `knowledge_file`：原始文件元数据与存储引用。
- `knowledge_chunk`：绑定具体版本，保存页码/章节/段落定位和向量。

上传文件先存储、解析和预览，发布后才可检索。同一来源同一时刻只允许一个当前发布版本；查询仍以时间和权限标签做数据库前置过滤。文件内容通过 `ObjectStore` 接口访问，开发可使用项目数据目录，生产可接对象存储。

**Rationale**

版本号字段无法独自表达同一来源的历史版本、解析失败、原文件与页码定位。分层模型可追溯回答使用的确切文件版本。

**Alternatives considered**

- 每次上传复制一条现有 `knowledge_document`：难以建立来源关系和当前版本唯一性。
- 将文件二进制直接存 PostgreSQL：备份和大文件读写成本较高，不作为默认方案。

### Decision 11：策略采用不可变版本和确定性优先级

**Choice**

策略草稿可编辑，发布后不可覆盖。运行时匹配顺序为 `user > dept > tenant > global`，同范围使用最新生效版本；冲突和非法阈值在发布前拒绝。每个任务保存命中的策略版本快照，在途任务默认按快照继续，管理员只能通过显式迁移动作改变。

**Rationale**

当前 upsert 会丢失历史配置，无法复现某次审批为何选择某规则。固定优先级使灰度行为可解释。

**Alternatives considered**

- 直接覆盖当前策略：操作简单但不可审计、不可安全回滚。
- 引入通用规则 DSL：P1 只需有限场景和字段，增加学习与安全成本。

### Decision 12：审计事件与运行 Span 分离但用 trace_id 关联

**Choice**

`audit_event` 继续作为不可修改的业务/安全事件，扩展规范化动作、主体、资源、结果和策略版本。新增 `runtime_span` 与 `model_usage` 保存运行级数据：run_id、trace_id、节点、工具、开始结束、耗时、错误分类、模型、token 是否已知和转人工标志。

审计导出采用受控导出任务，记录筛选条件哈希、申请人、脱敏策略、行数、文件引用和过期时间。P1 观测页面直接从 PostgreSQL 聚合；数据量增长后可在不改业务事件契约的前提下接 OpenTelemetry/指标平台。

**Rationale**

业务审计强调不可抵赖和长期追溯，运行 Span 强调高频性能与故障诊断；混在一表会造成字段稀疏、保留期冲突和权限扩大。

**Alternatives considered**

- 所有数据都写审计表：查询与保留策略难以兼顾。
- P1 强制部署外部 APM：会提高本地运行和交付门槛。

### Decision 13：采用 Alembic 扩张—迁移—收缩策略

**Choice**

建立当前数据库基线版本，后续每批通过 Alembic：

1. 扩张：新增兼容表/可空字段/索引。
2. 迁移：回填现有 MVP 数据，应用同时兼容新旧读法。
3. 切换：新写入使用新模型，运行一致性检查。
4. 收缩：只在独立后续迁移移除旧字段或旧路径。

生产启动只检查迁移版本，不自动 `create_all`；开发可通过明确命令初始化。迁移前记录备份和恢复点，破坏性收缩必须单独报备。

**Rationale**

大范围一次性重构会让现有任务无法读取，也无法安全回滚。分阶段迁移允许逐批验收。

**Alternatives considered**

- 删除并重建数据库：违反保留现有数据的要求。
- 永久保留 `create_all`：不能表达列变更、回填或回滚。

### Decision 14：测试必须以数据库身份和环境双重隔离

**Choice**

集成测试使用名称带 `_test` 的独立数据库和独立连接配置。清理夹具在执行前同时验证：`ENVIRONMENT=test`、数据库名后缀、显式允许清理标志。默认测试命令不接受开发 `.env` 的数据库地址。前端增加组件测试，关键角色流程使用 E2E；真实 OA 使用 HTTP 契约 Mock，不依赖生产系统。

**Rationale**

当前 API 测试会 TRUNCATE 数据库，仅靠开发者记忆规避风险不可靠。

**Alternatives considered**

- 每个测试使用事务回滚但仍连接开发库：误配置或非事务外部操作仍可破坏数据。
- 全部改成 SQLite：pgvector、JSONB、锁和 PostgreSQL 约束行为不同，不能覆盖关键风险。

### Decision 15：API 演进采用兼容窗口和统一写入信封

**Choice**

现有 `/api/agent/threads`、`/messages`、`/interrupts/{id}/resume` 等接口在 B1～B3 保持可用；响应逐步补充结构化字段。新领域接口包括：

| 领域 | 主要接口 |
| --- | --- |
| 任务 | `GET /api/tasks`、`GET /api/tasks/{id}`、`POST /api/tasks/{id}/retry`、`POST /api/tasks/{id}/handoff` |
| 请假 | `POST /api/leaves`、`PATCH /api/leaves/{id}`、`POST /api/leaves/{id}/submit`、版本与差异查询 |
| 审批 | `GET /api/approvals/inbox`、`GET /api/approvals/{id}`、`POST /api/approval-nodes/{id}/decisions` |
| 人工/工单 | 人工队列受理/回写、工单草稿确认/合并/分派/反馈接口 |
| 管理 | 知识上传/版本发布、策略版本发布/回滚、降级接口 |
| 审计运维 | 审计查询/导出、运行指标/trace 下钻接口 |

所有写请求通过 Header `Idempotency-Key` 或请求体命令 ID 提供幂等键，响应统一包含 `request_id`、`trace_id`、业务状态和结构化错误。旧 interrupt resume 最终转调审批/工单领域命令，并在前端迁移完成后标记弃用。

**Rationale**

完全替换接口会立即破坏当前页面和验证文档；兼容转调允许每批独立上线。

**Alternatives considered**

- 直接发布 `/api/v2` 并复制所有路由：会长期维护两套实现，当前规模没有必要。

### Decision 16：文件和敏感内容采用引用存储与分级摘要

**Choice**

附件和知识原文件不进入 LangGraph state、审计输入或普通日志。数据库只保存存储引用、哈希和必要元数据。消息、人工交接与审计分别定义允许字段；身份证明、健康材料和联系方式默认脱敏。下载使用短期授权并记录访问审计。

**Rationale**

请假附件和完整对话可能含敏感信息，复制到多个状态和日志会扩大暴露面和删除难度。

**Alternatives considered**

- 直接保存 Base64 到 JSONB：体积和敏感数据扩散不可控。

## Data Ownership And Consistency

| 数据 | 内置模式权威 | 真实 OA 模式权威 | 本地保存内容 |
| --- | --- | --- | --- |
| 身份/组织/角色 | 认证/开发目录适配器 | 企业 SSO/OA | 短期声明与审计摘要 |
| 请假申请 | 本地领域表 | 外部 OA | 版本化交互快照、外部 ID、哈希 |
| 审批实例/节点 | 本地领域表 | 外部流程引擎 | 状态投影、决定审计、对账信息 |
| 工单 | 本地工单表 | 外部工单系统 | 智能上下文、外部 ID、状态投影 |
| 会话/Checkpoint | 本地 PostgreSQL | 本地 PostgreSQL | 完整编排状态与恢复点 |
| 知识/策略/审计 | 本地 PostgreSQL | 本地 PostgreSQL | 权威记录 |

真实 OA 模式不做无条件双写。外部写入成功后保存本地投影；响应不确定时标记 `UNKNOWN` 并对账。定期对账只修正投影，不伪造人工决定。

## Frontend Information Architecture

导航按权限显示但不承担授权：

- 所有用户：智能助手、我的任务、我的请假、我的工单。
- 审批人：审批待办。
- 客服：人工队列、客服工单台。
- 管理员/知识运营：策略与灰度、知识治理、降级控制。
- 审计/运维：审计中心、运行观测。

请假采用“列表—表单—预检—审批进度—版本差异”页面链；工单采用“可编辑草稿—确认—详情/反馈”；所有详情页统一展示结构化状态、责任人、下一步、错误和 trace_id。切换菜单后由 URL 和服务端数据恢复，不依赖单一 Pinia 实例。

## Failure And Recovery Strategy

| 故障点 | 行为 | 恢复方式 |
| --- | --- | --- |
| 模型/检索失败 | FAQ 不猜测，转人工；业务确定性流程继续可用 | 人工处理或恢复后重新检索 |
| 余额/组织依赖失败 | 请假暂停，不建审批实例 | 授权重试或使用外部 OA 原路径 |
| 外部写响应不确定 | 幂等记录置 `UNKNOWN`，禁止新键重发 | 按原键查询/重试和对账 |
| 通知失败 | 不回滚已成功审批决定，记录待补发 | 幂等补发并展示通知状态 |
| 应用重启 | 权威业务状态不受影响 | Checkpoint + 权威状态对账恢复 |
| 智能路径关闭 | 新请求走确定性/原 OA 路径 | 管理员健康确认后重新启用 |

## Security Boundaries

- 前端角色切换仅保留为开发演示能力，生产构建不允许任意切换用户。
- 认证、资源授权、动态工具白名单和领域状态校验都在后端执行。
- 外部文件先做类型、大小、内容解析和安全扫描状态检查；未通过不得发布或作为审批依据。
- 用户文本、知识内容和附件解析文本均视为不可信数据，不得覆盖系统策略或工具权限。
- 导出、文件下载、策略发布、降级、审批决定和人工接管全部记录操作者与 trace_id。

## Rollout Plan

1. **B1 底座**：迁移基线、测试隔离、统一命令/错误、授权服务骨架和兼容 facade。
2. **B2 请假纠正**：先在现有 Mock 请假流引入节点级授权、决定幂等和安全恢复。
3. **B3 FAQ/工单纠正**：在不新增完整客服台前完善草稿确认、人工交接数据和权限一致性。
4. **B4～B8**：依照提案逐批增加正式页面、领域实体、治理、观测和真实 OA；每批开工前单独报备。

每批使用功能开关控制新旧路径。迁移和实现先在独立测试库验证，再在开发库进行非破坏升级。旧路径只有在数据对账、自动测试和手动验收均通过后才停止写入。

## Risks And Trade-Offs

| 风险/取舍 | 影响 | 缓解措施 |
| --- | --- | --- |
| P1 正式化实体数量显著增加 | 开发和迁移复杂度上升 | 按 B1～B8 分批，先兼容再收缩；每批独立验收 |
| 内置和外部 Provider 能力可能不完全一致 | 某些企业只能启用部分功能 | 能力探测、明确降级，不以 Mock 静默补能力 |
| 实时权限复核增加延迟和外部依赖 | 工具调用 P95 上升 | 短时缓存非高风险声明，高影响写入强制实时复核并观测耗时 |
| PostgreSQL 承担初期运行指标 | 高频数据可能增长快 | 设保留期和索引；契约预留 OpenTelemetry 导出 |
| 不引入通用流程引擎 | P1 之外流程复用有限 | 本阶段只保证请假；未来新增单据时重新评估，而非提前过度设计 |
| 兼容窗口同时存在新旧 API | 短期维护面扩大 | 记录弃用调用，前端迁移完成后按独立收缩批次移除 |
| 文件存储具体后端未绑定 | 生产部署需选择对象存储 | 使用 `ObjectStore` 契约；B6 开工报备时根据部署环境确认实现 |

## Validation Strategy

- 领域状态机：单元测试覆盖合法/非法迁移、越级、并发决定、驳回重提和节点升级。
- Provider：同一契约套件运行于 builtin、mock 和 real HTTP stub。
- 数据迁移：从当前 MVP 样本备份恢复后升级，验证行数、外键、状态映射和重复执行。
- API：独立测试库覆盖权限撤销、幂等冲突、恢复、人工交接和统一响应。
- 前端：组件测试覆盖表单和状态；E2E 覆盖员工、审批人、客服、管理员、审计角色。
- 非功能：依赖超时、进程崩溃点、服务重启、降级开关、提示注入、越权、性能和备份恢复演练。
- 手工验收：每批更新验证文档，最终以页面路径覆盖 F-001～F-044。
