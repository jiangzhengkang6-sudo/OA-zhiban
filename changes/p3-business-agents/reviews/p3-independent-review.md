### I2. Resolved: Contract Persistence Failures Are Classified As Model Failures

At `backend/app/services/contract_service.py:225`, the generation recovery try block includes node-state persistence, runtime span insertion and `session.commit()` at `:227` onward, plus review-version insertion and model-usage persistence at `:244` onward. The broad handler at `:253` rolls back, reloads the record and saves PAUSED. A trace flush/commit or review-version persistence failure is therefore converted into a successful model-recovery result instead of remaining a database failure. Previously committed node state is retained, but persistence faults must not become evidence that the analysis dependency failed; C5 requires controlled node recovery and atomic final business/ledger persistence.

Latest repair catches recoverable exceptions only while advancing the graph stream. Row reload/authorization, node-state persistence, runtime spans, checkpoint commits, final version/usage insertion and command completion sit outside that handler and propagate failures. The stream is closed in finally. The request session closes an aborted transaction; prior committed checkpoints remain PROCESSING with the original lease, and stale-run retry uses a new command key after 130 seconds. The original pending key is blocked, preventing uncertain replay from creating a second revision. Inspected both checkpoint and finalize fault tests: they assert PROCESSING rather than PAUSED, no review version after failure, then one recovered version via stale retry. The parent reports these tests passed; this reviewer did not execute their database fixture. I2 is resolved.
