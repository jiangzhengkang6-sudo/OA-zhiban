# 技术栈全景详解：功能、选型原因与技术优势

> 依据 `backend/requirements.txt`、`frontend/package.json`、`docker-compose.yml` 三处依赖清单交叉核实。每一项技术按三个维度展开：**项目中的具体用法**（它到底干了什么活）、**为什么选它**（当时的决策依据）、**技术优势与对比**（和同类替代方案比强在哪、为什么没选别人）。

---

## 一、智能体与 AI 层（项目灵魂）

### 1.1 LangGraph —— 全系统编排核心

**项目中的具体用法**

整个系统一共挂了 9 个业务智能体：审批、客服问答、工单、会议、文档、邮件、任务、报表、合同。每个业务被实现为一个**独立的状态图（StateGraph）**，图里定义了状态对象（当前节点、上下文、中间产出）和节点间的边。SuperAgent 作为入口节点负责意图识别：用户一句话进来，它判断这句话属于哪个业务域，然后把任务路由到对应的子图上。比如用户说"帮我请个假"，SuperAgent 识别后进入审批子图，子图内部走"材料预检 → 规则路由 → 人工审批 → 结果通知"的流转。图与图之间通过共享状态传递上下文，转人工时携带完整对话历史。

**为什么选它**

最初的需求是编排"带人工介入的长流程"。审批流天然不是线性的：预检不通过要打回、审批人可以驳回重提、超时要升级、会签要等所有人——这些是**有环、有分支、有中断点**的图结构。当时对比过三类方案：链式编排（LangChain Sequence）、Dify 这类低代码平台、以及 LangGraph 的图编排。链式结构表达不了回环；低代码平台把逻辑托管在平台侧，自定义 HITL 和幂等控制反而受限。LangGraph 的状态图模型让"流程现在走到哪、下一步可能去哪"成为显式可查的状态，这正是审批场景需要的。

**技术优势与对比**

- **图 vs 链**：条件边（conditional edges）一条定义就能表达"金额 ≥500 加签经理"，链式框架要靠代码里 if/else 拼接，流程一复杂就失控
- **原生 HITL 支持**：`interrupt` 机制让图在人工审批节点天然暂停，配合 Checkpointer 可以停一天再恢复——AutoGen、CrewAI 这类框架以多智能体对话为主，对"流程中断等人"这种场景支持是后补的
- **状态显式化**：每一步的状态变更都可审计可重放，调试时直接看状态快照，不用靠日志倒推
- **生态与文档**：LangChain 系社区和资料最多，出问题能搜到解法——对个人开发者，这比框架本身的先进性更实际

### 1.2 langgraph-checkpoint-postgres —— 断点恢复与不重放保证

**项目中的具体用法**

LangGraph 的每个节点执行完毕，Checkpointer 把整个状态（含已完成节点列表、上下文数据）序列化写入 PostgreSQL。服务重启后，进行中的流程从最近的检查点继续，而不是从头跑。这个能力经过了硬验证：**两次真实进程重启演练 + 13 条命令重放，零重复业务写入**。它和业务层的幂等键（每笔单据唯一业务号）形成双保险：检查点保证"不从头跑"，幂等键保证"就算重跑也不重复写"。

**为什么选它**

审批流程可能跨天——领导今天不批，流程就挂着等。内存态（进程重启即丢）、本地文件（多实例不共享）都撑不住这个场景。Checkpointer 官方支持 Memory / SQLite / PostgreSQL 三种后端，选 PostgreSQL 是因为它和业务数据库同库，运维体系（备份、监控、权限）完全复用，个人开发不引入任何新的运维负担。

**技术优势与对比**

- **与业务数据同库**：一次 pg_dump 同时备份业务数据和流程状态，恢复演练时两边一致——如果用 Redis 做检查点，就得维护两套备份策略并保证一致性快照，运维复杂度翻倍
- **官方维护、版本同步**：`langgraph-checkpoint-postgres` 是 LangGraph 官方包，随主框架版本演进，不存在第三方适配滞后的风险
- **"重启不重放"是护城河**：很多 Agent demo 死在"重启后重复执行了已完成的写操作"。检查点 + 幂等键 + 写前对账这套组合，是把 demo 变成可落地系统的关键工程，也是本项目相对一般 Agent 项目的差异化点

### 1.3 DeepAgents —— 复杂长文档的"计划-执行"智能体

**项目中的具体用法**

专门处理长合同这类超出单次上下文窗口的复杂文档。流程是：DeepAgents 先对任务做**计划拆解**（要提取哪些条款、分析哪些风险），再把长文**分块读取**逐段处理。在其之上我搭了一个**四节点子图**，分别跑条款提取、风险分析、证据定位、结果汇总。给它套了两层约束：**工具白名单**（只能调我注册的读取工具，不能自己发明调用）和**调用预算**（限制总调用次数，防止死循环烧 token）。

**为什么选它**

长文档分析本质是"规划 + 多步执行 + 中间产物管理"，从零手写 planning 循环工作量大且容易出各种边界问题。DeepAgents 开箱提供了计划拆解、虚拟文件系统、子智能体调度这些能力，正好覆盖需求。版本锁定 0.4.11 是刻意为之：Agent 框架迭代极快，不锁版本会出现"上周测试通过的流程，这周依赖升级后行为变了"，对要写 420 项回归测试的项目是灾难。

**技术优势与对比**

- **内置 planning 循环**：计划-执行-反思的循环框架内置，对比裸用 Function Calling 手写多轮任务分解，开发量省一个量级
- **约束边界是亮点**：白名单 + 预算的"缰绳"设计可以主动讲——它体现了"给智能体放权但不失控"的工程思路，和全系统 HITL 理念一脉相承
- **锁版本的工程纪律**：面试被问"为什么锁这么老的版本"时，答案是可复现性优先于新特性——这是工程化项目和个人玩具的分水岭

### 1.4 LangChain Core —— 智能体基础抽象层

**项目中的具体用法**

作为 LangGraph 的底层依赖，同时承担多模型统一接入：所有 LLM 调用（对话、预检、纪要、RAG 回答）都走 LangChain Core 的模型抽象接口，消息格式、工具定义（Tool Calling 协议）、流式输出全部标准化。

**为什么选它**

它是 LangGraph 生态的地基，既然编排层选了 LangGraph，接入层顺理成章用它。更重要的是它的**模型无关抽象**：切模型只换一个类，业务代码零改动。

**技术优势与对比**

- **主备切换的底座**：DeepSeek（主）和火山方舟 ARK（备）都兼容 OpenAI 协议，通过 LangChain Core 抽象后，`LLM_FALLBACK_PROVIDER` 环境变量就能完成主备切换，主通道故障秒级降级——这套 fail-over 设计面试时可以主动讲
- **Tool Calling 标准化**：工具定义写一次，任何兼容模型都能用，避免了每接一个模型重写一遍调用协议

### 1.5 pgvector —— RAG 向量检索（PostgreSQL 扩展）

**项目中的具体用法**

公司的制度、规则、办事要求文档经切分、Embedding 后存入 PostgreSQL 的 vector 字段。智能助手回答制度类问题时先做相似度检索，把最相关的文档块注入提示词，**回答强制附上出处**（引用来源文档），检索不到或置信度不足时**直接转人工**——坚决不让模型编造制度。

**为什么选它**

知识库规模在部门级是万级文档块，pgvector 的 HNSW 索引绰绰有余。关键是架构权衡：如果引入 Milvus / Qdrant / Elasticsearch，就多一个需要部署、监控、备份、保证与主库数据一致的组件。个人开发 + 部门级落地，**少一个组件的价值大于多一档检索性能**。

**技术优势与对比**

- **同库同事务**：写业务单据和写向量在同一个 PG 事务里完成，天然避免"业务写成功、向量写失败"的双写不一致——这是独立向量库做不到的（它们没有跨库事务）
- **运维归一**：备份、权限、审计、监控全部复用 PG 现有能力
- **成本为零**：`pgvector/pgvector:pg16` 官方 Docker 镜像内置扩展，无需自建向量服务
- **对 RAG 效果而言**：万级规模下 HNSW 检索质量与专业向量库无实质差异；真到百万级再迁移不迟，且因为走的是 SQL 接口，迁移只动数据层不动业务层

### 1.6 DeepSeek API —— 主 LLM 供应商

**项目中的具体用法**

承担全部主力推理任务：RAG 问答的回答生成、请假/报销的材料预检结论、会议转写文本的纪要生成、工单分类等。通过环境变量 `DEEPSEEK_BASE_URL / DEEPSEEK_API_KEY / DEEPSEEK_CHAT_MODEL` 配置，超时由 `LLM_TIMEOUT_SECONDS` 统一控制。

**为什么选它**

国产模型里推理能力第一梯队、价格显著低于国际模型、API 完全兼容 OpenAI 协议。对"高频调用 + 个人承担成本"的 RAG 问答场景，单价是硬指标。

**技术优势与对比**

- **OpenAI 兼容**：接入层复用 LangChain 的 OpenAI 兼容类，配置即接入
- **中文能力强**：制度问答、会议纪要都是中文密集任务，中文语料质量直接影响产出
- **成本可控**：高频问答场景下 token 费用是持续成本，DeepSeek 单价让这个成本几乎可以忽略

### 1.7 火山方舟 ARK（豆包）—— 备用 LLM 与故障切换

**项目中的具体用法**

作为 `LLM_FALLBACK_PROVIDER` 配置的备用通道：主通道 DeepSeek 超时或报错时，系统自动切到 ARK 完成当次调用，用户无感。同样 OpenAI 兼容协议，`ARK_BASE_URL / ARK_API_KEY / ARK_CHAT_MODEL` 环境变量配置。

**为什么选它**

单一 LLM 依赖是可用性单点——智能层的所有功能（问答、预检、纪要）都压在一个 API 上，供应商限流或故障等于系统智能能力全灭。必须有热备。

**技术优势与对比**

- **秒级 fail-over**：环境变量级配置，主备同构（都走 OpenAI 兼容抽象），切换逻辑只是"主失败 → 试备"
- **设计哲学可以讲**：LLM 故障的兜底不是"硬等主通道恢复"也不是"直接报错"，而是备通道顶上；备通道也挂了，流程回退到纯人工路径——三层兜底，智能层故障永远不影响业务可用性

### 1.8 腾讯云 SDK（TRTC 实时音视频 + 录音转写）—— 会议模块全链路

**项目中的具体用法**

服务端用 `tencentcloud-sdk-python-trtc` 做**入会签名（UserSig）签发**——用户点"进入会议"时，后端用 `TRTC_SDK_SECRET_KEY` 为该用户签发有时效（默认 3600 秒）的凭证，防止未授权入会。录音转写开启后（`MEETING_TRANSCRIPTION_ENABLED`），会议音频走腾讯云转写服务（`bigmodel-zh` 模型、广州地域），转写结果回调进系统，交给 LLM 生成结构化会议纪要。

**为什么选它**

音视频基础设施（SFU 服务器、抗弱网、编解码）自研完全不现实，必须借云。选腾讯云是因为它一家同时覆盖了 Web 端组件（RoomKit）和服务端 SDK（UserSig 签发）与转写服务，全链路单供应商，不存在跨云联调。

**技术优势与对比**

- **差异化能力**：传统 OA 的会议模块止步于"能开会"；本系统做到"会后智能体自动读转写、出纪要"——转写是智能纪要链路的第一公里，也是选云服务时必须一并考虑的能力
- **安全设计**：UserSig 有时效 + SecretKey 只存在服务端，前端拿不到签名密钥——会议权限防伪是很多集成方案漏掉的点
- **回调机制**：转写完成走回调通知而非轮询，服务端无空转开销；回调带 key 校验防伪造请求

## 二、后端（FastAPI 体系）

### 2.1 FastAPI + Uvicorn —— 业务与接口骨架

**项目中的具体用法**

承载全部 REST 接口：认证、组织、审批、工单、会议、文档、邮件、报表等，以及接口级权限校验中间件。智能层的 LangGraph 代码与业务层同进程共享，SuperAgent 的入口 API 就是一个普通的 FastAPI 路由。Uvicorn（ASGI 服务器）承载异步请求。

**为什么选它**

两个决定性原因：① 与 LangGraph 同为 Python，智能层和业务层**同语言同进程**，共享数据模型、事务和工具函数——这是选 Django/Flask 也成立但选 Node/Java 就不成立的关键点（跨语言就得走 RPC，复杂度陡增）；② 原生异步，而本项目的大多数请求路径上都挂着 IO 等待（LLM 调用、数据库、外部 API），异步模型的吞吐收益是实打实的。

**技术优势与对比**

- **对比 Flask**：Flask 无原生异步、无内建校验，需要自己拼 Pydantic + 异步扩展；FastAPI 开箱即得
- **对比 Django**：Django 是全家桶但重，ORM/模板/Admin 对本项目是负担而非助力——项目只需要轻 API 层，Django 的"重"全是成本
- **自动文档**：Pydantic 模型即 OpenAPI 文档，前后端接口契约天然对齐，联调时前端对着 Swagger 写调用
- **依赖注入**：权限校验、数据库会话通过 Depends 注入，中间件逻辑与业务代码解耦，420 项测试里可以轻松替换依赖做 mock

### 2.2 Pydantic v2 / pydantic-settings —— 校验与配置中枢

**项目中的具体用法**

所有请求/响应体的结构校验（字段类型、长度、格式在进业务逻辑前就拦住）。`pydantic-settings` 管理全部环境变量——`docker-compose.yml` 里那几十个配置项（`OA_PROVIDER`、`AI_ENABLED`、`LLM_PROVIDER`、TRTC 密钥组、转写配置组……）全部由它加载、类型校验、给默认值。

**为什么选它**

FastAPI 原生搭档，且项目的配置面特别大：mock/real 切换、双 LLM 主备、TRTC 四个配置、转写六个配置——没有集中式配置管理必然失控。

**技术优势与对比**

- **v2 Rust 内核**：校验性能比 v1 高一个量级，高并发下不再是瓶颈点
- **配置即架构**：`OA_PROVIDER=mock→real`、`AI_ENABLED=true→false` 这些开关让"智能层可一键降级""mock 可换真实现"成为改环境变量而不是改代码——这是架构级的可测试性和可运维性，也是整个"内桥"设计的落地点

### 2.3 SQLAlchemy 2.0 + asyncpg / psycopg3 —— 数据访问层

**项目中的具体用法**

异步 ORM（asyncpg 驱动）承载运行时的全部数据库读写；psycopg3 作为同步驱动覆盖迁移等场景。全部业务表（组织、单据、审计、会话、向量）的建模与事务都在这层。

**为什么选它**

SQLAlchemy 是 Python ORM 的事实标准，2.0 风格的类型提示和异步支持让它与现代 FastAPI 完全匹配。选它而非轻量替代（如 Tortoise-ORM）是因为生态成熟度和 Alembic 迁移工具的无缝衔接。

**技术优势与对比**

- **全链路异步**：asyncpg 是 PG 驱动中性能最强的实现之一，配合 FastAPI 的 async 路由，数据库等待不再阻塞 worker
- **双驱动策略**：异步驱动跑业务、同步驱动跑迁移，各取所长
- **类型安全**：2.0 声明式映射配合 mypy，字段改名这类错误在静态检查期暴露

### 2.4 Alembic —— 数据库迁移版本管理

**项目中的具体用法**

PRD 从 V1.2 迭代到 V1.4，表结构跟着里程碑演进（M1 数据模型、V2 的员工状态/代理人/权限三档字段扩展），每一次结构变更都是一个版本化的迁移脚本，进 Git、可重放、可回滚。

**为什么选它**

手工改库不可追溯、环境间结构漂移是必然事故。个人开发更要防"我这能跑，部署机上跑不起来"。

**技术优势与对比**

- **迁移即代码**：`alembic revision` 自动 diff 生成变更脚本，人工审查后入库
- **面试可讲的具体价值**：三个 PRD 版本迭代、多里程碑并行开发，任何环境的数据库都能从零重放到最新结构——这就是"环境可重建"能力

### 2.5 PyJWT + argon2-cffi —— 认证安全双件套

**项目中的具体用法**

argon2-cffi 做密码哈希（注册/改密时哈希存储，登录时验证）；PyJWT 做 JWT 签发与校验（登录后发 token，后续请求带 token 鉴权，`AUTH_JWT_SECRET` 签名，`AUTH_COOKIE_SECURE` 控制 Cookie 安全属性）。

**为什么选它**

认证是安全底座，这两个库都是各自领域的"标准答案"，没有理由自造轮子。

**技术优势与对比**

- **argon2 优于 bcrypt**：argon2 是 2015 年密码哈希竞赛（PHC）冠军算法，抗 GPU/ASIC 暴力破解能力优于 bcrypt，且内存硬化参数可调——面试被问"为什么不用更常见的 bcrypt"，这就是答案
- **JWT 无状态会话**：服务端不存会话表，水平扩展无会话粘滞问题；为 V2 部门级 HTTPS 部署预留了完整的安全配置面（Secure Cookie、CORS 白名单 `AUTH_ALLOWED_ORIGINS`）

### 2.6 pypdf / Pillow / python-multipart —— 附件处理三件套

**项目中的具体用法**

pypdf 解析 PDF（合同、制度文档分页提取文本，喂给 DeepAgents 分块分析或进 RAG 知识库）；Pillow 处理图片（缩略图、格式校验）；python-multipart 承接文件上传表单。

**为什么选它**

附件是 OA 刚需，且 RAG 的知识来源之一就是员工上传的 PDF 制度文档——附件处理直接服务质量链上游。

**技术优势与对比**

- **纯 Python、轻依赖**：不引重量级文档服务（如独立 OCR 服务），PDF 原生文本提取够用，控制了部署面
- **与智能层衔接**：pypdf 分页提取的文本天然适合 DeepAgents 的分块读取节奏

### 2.7 httpx + respx —— 外部调用与 mock 测试

**项目中的具体用法**

httpx（异步 HTTP 客户端）承担全部外部调用：LLM API、OA bridge、腾讯云转写回调验证。每个外部调用都有显式超时（`OA_TIMEOUT_SECONDS`、`LLM_TIMEOUT_SECONDS`、`MEETING_LLM_TIMEOUT_SECONDS` 各自独立配置）和重试策略（`OA_READ_RETRIES`）。respx 在测试中拦截并 mock 这些 HTTP 调用。

**为什么选它**

requests 是同步的，配不上全异步链路；httpx 是异步生态的默认选择，respx 是其官方配套 mock 库，两者 API 同构。

**技术优势与对比**

- **超时是架构而非细节**：外部依赖永远不能拖死主流程——每类外部调用独立超时配置，意味着 LLM 慢不影响 OA bridge 的响应
- **离线全量回归**：420 项测试通过 respx 隔离了所有真实外部服务，可以在无网环境全量重跑——测试稳定性和速度都上了台阶，这也是"测试数字敢写进简历"的底气

## 三、前端（Vue3 体系）

### 3.1 Vue 3 + TypeScript —— 组件化 UI 与类型安全

**项目中的具体用法**

全部工作台页面：不同角色登录后看到的功能模块由路由与权限控制（"职位越高、解锁功能越多"），审批卡片、待办列表、会议页、知识问答等界面均组件化开发。TypeScript 全量覆盖，接口层类型与后端 Pydantic schema 手工对齐。

**为什么选它**

单人全栈开发，学习曲线和中文生态是现实考量。Vue3 的 Composition API 在抽离复用逻辑（如权限判断、轮询刷新）时比 Options API 清晰得多。

**技术优势与对比**

- **前后端类型对齐**：TS 接口定义和 FastAPI 的 Pydantic 输出字段一一对应，字段改名这类破坏性变更在编译期报错而不是运行期白屏
- **对比 React**：React 生态更大但本项目的收益点不在生态而在开发效率，Vue3 模板语法 + 中文文档对单人快速出活更友好
- **Composition API**：审批页的"轮询待办状态 + 权限判断 + 表单校验"三块逻辑各自抽成 composable，页面代码只剩组装

### 3.2 Element Plus —— 中后台组件库

**项目中的具体用法**

工作台的全部业务组件：数据表格（待办/已办列表）、表单（请假/报销申请单）、对话框、消息通知、日期选择器等，配合 `@element-plus/icons-vue` 图标体系。

**为什么选它**

OA 是典型的中后台应用，Element Plus 对这类场景的组件覆盖率最高，且是 Vue3 生态里文档最完善、迭代最活跃的组件库。

**技术优势与对比**

- **中后台全覆盖**：表格的分页/排序/筛选、表单的校验规则都是现成的，自研这些基础组件的时间可以全部投入业务
- **对比 Ant Design Vue**：两者能力接近，选 Element Plus 主要因为中文文档质量和社区活跃度在 Vue3 生态更稳

### 3.3 Pinia —— 全局状态管理

**项目中的具体用法**

登录态、当前用户角色与权限集、待办未读数等跨页面共享状态集中在 store；路由守卫读取权限 store 决定页面可见性，界面组件读取角色 store 决定功能可见性。

**为什么选它**

Vue3 官方推荐方案，替代 Vuex。类型推导好、样板代码少。

**技术优势与对比**

- **对比 Vuex**：无 mutation 层、天然 TS 类型推导，代码量减一半
- **权限集中管理**：角色权限判断只写一份（store 的 getter），路由守卫和组件共用——权限逻辑散落各处是安全漏洞的温床

### 3.4 Vue Router —— 角色化路由

**项目中的具体用法**

按角色组织路由表，路由守卫做两级控制：未登录跳登录页；已登录但无权限的角色访问受限页面时拦截。

**为什么选它**

与 Pinia 同属 Vue 官方全家桶，集成零成本。

**技术优势与对比**

- **守卫即门禁**：权限控制收口在路由层，页面内部不需要重复判断"能不能进"——前端权限控制负责体验，真正的安全由后端接口级校验兜底（这个分工面试要能说清：前端权限挡君子，后端校验防小人）

### 3.5 腾讯云 RoomKit Web Vue3（TUIKit）—— 系统内视频会议

**项目中的具体用法**

会议页直接嵌入 RoomKit 的 Vue3 组件，摄像头、麦克风、屏幕共享、屏幕录制、成员管理全部由 TUIKit 提供；入会凭证由后端签发的 UserSig 注入。

**为什么选它**

会议 UI（视频画面布局、设备管理、信令状态）自研工作量以月计，RoomKit 提供的 Vue3 原生组件十几行就能拉起完整会议界面，且与后端 TRTC SDK 同供应商，UserSig 即插即用。

**技术优势与对比**

- **UI 层与服务层同源**：RoomKit（前端 UI）+ TRTC SDK（后端签发）一家供应商，版本兼容性由腾讯云自己保证
- **对比裸用 TRTC SDK**：裸 SDK 只有底层能力，UI 全要自写；RoomKit 把"能用的会议界面"变成了配置问题

### 3.6 Axios —— HTTP 请求层

**项目中的具体用法**

统一请求实例：请求拦截器注入 JWT token；响应拦截器统一处理 401（跳登录）、500（友好错误提示）；文件下载、上传走同一实例。

**为什么选它**

拦截器机制成熟，横切逻辑（认证、错误处理）一处配置全局生效。

**技术优势与对比**

- **横切关注点收口**：token 注入和错误处理不散落在各页面，改一处全局生效——这与后端"依赖注入做权限"是同一设计思想在前端的投影

### 3.7 Vite + vue-tsc + Sass —— 构建与样式工具链

**项目中的具体用法**

Vite 承担开发服务器与生产构建；`vue-tsc -b` 在构建前做全量类型检查（build 脚本里先 tsc 后 vite build，类型错误挡在发布前）；Sass 写主题样式变量。

**为什么选它**

Vite 已是 Vue3 默认标准；类型检查卡在构建入口是防止"能跑但带病"的代码上线的机制。

**技术优势与对比**

- **秒级热更新**：ESM 按需编译，开发体验远超 webpack 时代的全量打包
- **类型门禁**：`build` = `vue-tsc -b && vite build`，类型不过构建不过——工具链层面的质量门

## 四、数据与部署

### 4.1 PostgreSQL 16 —— 单库三合一

**项目中的具体用法**

一个数据库实例承载三类数据：① 业务数据（组织、单据、流程状态）；② 审计日志（每次写操作与 LLM 决策留痕）；③ 向量知识库（pgvector 的 embedding 字段 + HNSW 索引）。Docker 数据卷 `oa_pgdata` 持久化，健康检查 `pg_isready` 保证就绪后才启动后端。

**为什么选它**

"单库三合一"是刻意的架构决策：个人开发 + 部门级负载（几十人、日几百单据），PostgreSQL 单机性能远超所需，而把它拆成"业务库 + Redis + 向量库"三个组件，运维成本直接三倍，收益为零。

**技术优势与对比**

- **事务性审计**：业务写入与审计写入同事务提交——"业务成功但审计丢失"在架构上不可能发生，这是审计可信的根基
- **单备份点**：每日 pg_dump 即全量备份（含向量），恢复演练目标 ≤10 分钟
- **对比"专业组合"**：Milvus（向量）+ Redis（缓存）+ PG（业务）是"标准"互联网架构，但对部门级规模是过度设计——组件数量本身就是故障源
- **pgvector 官方镜像**：`pgvector/pgvector:pg16` 内置扩展免编译，compose 拉起即用

### 4.2 Docker Compose —— 环境编排与 mock/real 切换枢纽

**项目中的具体用法**

一个 compose 文件编排全部服务（db + backend），环境变量集中注入：认证组（`AUTH_*`）、智能开关组（`AI_ENABLED`、`LLM_PROVIDER`、`LLM_FALLBACK_PROVIDER`）、OA 适配组（`OA_PROVIDER`、`OA_TIMEOUT_SECONDS`、`OA_READ_RETRIES`）、TRTC 组、转写组、双 LLM 组。数据库健康检查通过后后端才启动。

**为什么选它**

个人开发不需要 K8s 的编排能力，需要的是**环境一致性**和**配置即切换**。compose 文件本身就是部署文档。

**技术优势与对比**

- **配置即架构的落地点**：`OA_PROVIDER=mock→real` 一行环境变量完成"Mock 适配器 → 真实 OA"切换，不动一行代码——这是整个"内桥"设计的运行时入口；`AI_ENABLED=false` 一键降级到纯人工流程
- **对比 K8s**：部门级几十人规模，K8s 的自愈/扩缩容能力用不上，运维复杂度却高一个量级；compose + restart 策略 + 健康检查已覆盖需求
- **V2 平滑迁移**：未来搬部门服务器，整套 compose 原样带过去，改的只是几行配置

## 五、质量与测试

### 5.1 Pytest + pytest-asyncio —— 420 项后端回归

**项目中的具体用法**

覆盖全部后端模块的回归测试：认证、RBAC、审批链引擎（条件路由/会签或签/代理/超时升级）、幂等与对账、审计、各智能体子图、桥接层。异步链路用 pytest-asyncio 原生支持。

**为什么选它**

Python 测试事实标准。项目的测试策略是"外部全 mock、内部全覆盖"：respx 拦 HTTP、测试夹具装配 mock 数据，保证无外部依赖、可离线重放。

**技术优势与对比**

- **fixture 体系**：数据库状态、登录态、mock 适配器通过 fixture 统一装配，用例只写业务断言
- **异步原生**：LangGraph 流程、异步接口的测试与同步用例写法一致

### 5.2 Vitest + @vue/test-utils —— 58 项前端单测

**项目中的具体用法**

核心组件与 composables 的单元测试：权限 store、审批卡片渲染、表单校验逻辑等。

**为什么选它**

与 Vite 同内核共享配置，Vue3 生态默认测试方案。

**技术优势与对比**

- **零额外配置**：vitest 直接读 vite.config，无需独立配置体系
- **对比 Jest**：Jest 对 Vite/ESM 项目配置繁琐，Vitest 天然匹配

### 5.3 Playwright —— 端到端浏览器回归

**项目中的具体用法**

36 项 E2E 用例覆盖关键用户路径（登录 → 发起审批 → 审批 → 通知），同时跑桌面与移动两种视口。

**为什么选它**

单测证明组件正确，E2E 证明"用户真的能用"。选 Playwright 而非 Cypress 主要看多浏览器/多视口支持与自动等待机制。

**技术优势与对比**

- **一套脚本双视口**：桌面 + 移动布局回归共用用例，只切换 viewport 配置
- **自动等待**：内置等待元素就绪/网络空闲，flaky 率显著低于手写 sleep 的方案

## 六、选型总纲（面试背诵版）

**为什么是这套组合？三个约束决定了所有选型：**

1. **单人开发，能借的不造，能合的不拆**——音视频、转写、LLM 全部借云（TRTC/DeepSeek），向量检索不引独立库（pgvector 单库三合一），会议 UI 用现成组件（RoomKit）。省下的每一个组件，都是不用运维的组件。
2. **安全落地是底线，不是加分项**——幂等键、事务性审计、fail-closed 的权限校验、可一键降级的智能路径、断点不重放（Checkpointer + 幂等双保险）。这套可靠性组合是把 Agent demo 变成可落地系统的分水岭。
3. **智能与业务同语言**——Python 全栈让 LangGraph 智能层和 FastAPI 业务层共享代码、数据模型与事务。跨语言架构就得引入 RPC 和两套运维，单人开发养不起。

**一句话全景**：LangGraph 是灵魂（编排 + 断点恢复 + HITL），FastAPI 是骨架（业务 + 权限 + 事务），PostgreSQL + pgvector 是记忆（数据 + 审计 + 向量三合一），DeepSeek + DeepAgents 是大脑（推理 + 长文档分析，豆包热备），Vue3 + RoomKit 是门面（角色工作台 + 系统内会议），Docker Compose 把它们串成一条命令就能跑、一行配置就能切 mock/real 的整体。
