# OA 智能体管理系统 — 优化方向与优先级建议

> 版本：V1.0　日期：2026-11-02
> 基线段位：后端 305 个 py / 30,258 行；前端 138 个 vue+ts / 10,717 行；137 张表；39 个迁移；180 个测试文件 / 902 个测试函数
> 约束前提：单人维护、部门级（5-10 人试点起步）、本机/内网 Docker 部署。**所有建议都按"是否增加长期运维负担"过滤过**，重型方案（K8s、Redis 集群、微服务拆分）不列入。

## 二、P0：两周内做，投入产出比最高

### P0-1　前端主包瘦身（9.4 MB → 目标 < 800 KB）

**证据**：`dist/assets/index-CEMwtEjN.js` 9.4 MB，gzip 后 3.16 MB；包内 `TRTC` 字样出现 616 次、`RoomKit` 182 次。`src/main.ts` 第 8、9、13 行是根因：

```ts
import ElementPlus from 'element-plus'            // 全量组件
import 'element-plus/dist/index.css'              // 全量样式
import * as ElementPlusIconsVue from '@element-plus/icons-vue'  // 全量图标（千余个）
```

三个问题叠加：Element Plus 全量注册、图标全量全局注册、会议 SDK（RoomKit/TRTC，node_modules 中 `@tencentcloud` 占 31 MB）被打进主包而非会议页的懒加载 chunk。

**做法**（按收益排序）：
1. **图标按需**：删除 `import * as ElementPlusIconsVue` 与 `app.component` 批量注册循环，改为各页面按需 `import { Plus, Search } from '@element-plus/icons-vue'`。单这一步通常砍掉 1.5-2 MB。
2. **Element Plus 按需**：引入 `unplugin-vue-components` + `ElementPlusResolver`，去掉 `main.ts` 的全量 `ElementPlus` 与全量 CSS。
3. **manualChunks 分组**：在 `vite.config.ts` 里把依赖切成 `vendor-vue`（vue/router/pinia）、`vendor-element`、`vendor-meeting`（roomkit/trtc）三组；会议 SDK 必须只出现在 `MeetingView` 的动态 chunk 中。
4. **验证口径**：`npm run build` 后检查「主包 gzip < 300 KB、会议 SDK 只在进入会议页时才请求」。可用 `vue-tsc -b && vite build` 后的产物清单直接核对，不需要额外工具。

**预期收益**：首屏传输量下降 80%+（3.16 MB → 约 400-600 KB）；内网千兆环境下首屏可交互时间从 2-4 秒量级降到 1 秒内；会议页首次进入会有一个可感知的加载（这是正确的取舍——只有开会的人付这个成本）。
**工作量**：0.5-1 天。**风险**：图标改为按需后可能有遗漏，用 `vue-tsc` + 页面走查兜底。

---

### P0-2　补齐列表接口分页

**证据**：14 个 `list_*` 端点中，只有 `leaves`、`meetings`、`tasks` 带 `page/page_size`。以下端点无分页参数，直接返回全量：
`oa_leaves`、`oa_reimbursements`、`oa_workflows`、`oa_balances`、`policies`、`knowledge.documents`、`leaves.list_attachments` 等。

**做法**：
1. 定义统一分页契约（与已有三处保持一致）：入参 `page>=1, page_size<=100`，出参 `{items, total, page, page_size}`。
2. 服务层补 `COUNT` + `LIMIT/OFFSET`，并保证排序字段有索引（见 P0-3）。
3. 前端表格改服务端分页（Element Plus `el-pagination` + `@current-change`），去掉前端全量拉取后 slice 的写法。

**预期收益**：单据量到 5,000+ 条时，列表响应从"随数据量线性增长"变为常数；内存与序列化开销同步下降。这是部门级试点最容易先炸的地方——试点第一个月单据量就会过千。
**工作量**：1-2 天（7-8 个端点）。

---

### P0-3　建立慢查询基线并补复合索引

**证据**：137 张表只有 30 个 `index=True`；`tests/performance` 仅有 1 个基线文件；已有 31 处计时埋点但未汇总成基线。

**做法**：
1. 在 `oa-agent-db` 开启 `pg_stat_statements`（`shared_preload_libraries`），跑一周真实使用后取 `total_exec_time` Top10。
2. 优先核对三类高频查询的索引：
   - 待办列表：`(tenant_id, assignee_id, status, created_at desc)`
   - 单据列表：`(tenant_id, applicant_id, status, created_at desc)`
   - 通知出箱：`(status, next_attempt_at)`（worker 轮询用）
3. 把 Top10 的 `EXPLAIN (ANALYZE, BUFFERS)` 输出存进 `tests/performance/baselines/`，作为回归对照。

**预期收益**：待办/单据列表在万级数据下稳定 < 50 ms；避免"试点第三个月突然变慢"这类无法复现的问题。
**工作量**：1 天（开扩展 + 看 top10），索引按需另计。

---

### P0-4　覆盖率基线 + 最小 CI

**证据**：902 个测试、八类测试目录结构完整，但**没有任何覆盖率配置**，也没有 CI。测试的价值目前只体现在"本地跑过"。

**做法**：
1. `pip install pytest-cov`，在 `pytest.ini` 加 `--cov=app --cov-report=term-missing`，先只**记录**基线数字，不设门禁（否则会为了数字写垃圾测试）。
2. 生成一次 HTML 报告，重点看 `api/routers/` 与 `services/` 里未覆盖的分支——这些是回归风险最高处。
3. 加一个最小流水线（GitHub Actions 或本地 `pre-push` 钩子）：`pytest tests/unit -q` + `npm run test` + `vue-tsc`。三件套跑通即可，不做多环境矩阵。

**预期收益**：把"420 项通过"这类无法验证的说法换成可复现的数字；每次改动有自动兜底，个人开发时这一点比团队更重要（没人帮你 review）。
**工作量**：半天。

## 三、P1：一个月内做，解决结构性隐患

### P1-1　服务层按域收敛，处理双轨遗留

**证据**：79 个 service 文件中，同一业务域严重碎片化：
- meeting：`meeting_service` / `meeting_management_service` / `meeting_parser` / `meeting_generator` / `meeting_video_service` / `meeting_transcription_service`
- leave：`leave_application_service` / `oa_leave_service` / `oa_leave_graph_service`
- approval：`approval_service` / `oa_approval_service`

其中 `oa_*` 是自研正式链路，无前缀的是 P1-P3 演示链路遗留。前端 `navigation.ts` 已用 `mockOnly` 集合在 builtin 模式下隐藏旧入口，说明**旧链路已经没有用户路径**，但代码仍在参与维护成本。

**做法**：
1. 先量化：给旧链路 service 的入口函数加一条 debug 日志，跑 2-4 周，确认零调用。
2. 按域建子包：`services/meeting/`、`services/leave/`、`services/approval/`，把同域文件收进去，旧链路移入 `services/_legacy/` 并标注弃用日期。
3. 优先合并 approval（纯读路径多、风险最低），meeting 最后动（6 个文件耦合最深）。

**预期收益**：会议相关改动从"要在 6 个文件里找入口"变成 2 个文件；避免改错文件导致的线上行为不一致——这是当前最大的可维护性成本。
**工作量**：3-5 天（含回归）。**风险**：合并过程容易误删分支，必须依赖 P0-4 的覆盖率兜底后再做。

---

### P1-2　依赖可重现

**证据**：`requirements.txt` 24 项中多数是范围约束（`fastapi>=0.110,<1.0`、`langgraph>=0.2.40`、`SQLAlchemy>=2.0.25,<2.1`），只有 DeepAgents 单独锁了 `0.4.11`。已踩过一次坑（DeepAgents 迭代快导致行为漂移），但整体策略没统一。

**做法**：
1. `pip-tools`：维护 `requirements.in`（范围约束）+ 生成 `requirements.lock.txt`（精确版本 + 哈希），Docker build 用 lock。
2. 前端确认 `package-lock.json` 已入库（当前有 lock 文件，需确认是否被 `.gitignore` 排除）。
3. 升级流程固定为：改 `.in` → `pip-compile` → 跑 902 项测试 → 提交 lock 变更。

**预期收益**：半年后重建镜像仍能装出同一套版本；升级失败可一眼 diff 出是哪个包动了。
**工作量**：半天。

---

### P1-3　连接池与热点缓存

**证据**：`app/db/session.py:23` 只传了 `pool_pre_ping=True`，未设 `pool_size`，走 SQLAlchemy 默认 5。全项目缓存相关代码 5 处，组织树、流程定义、策略配置这类**低频变更、每次请求都读**的数据没有缓存。

**做法**：
1. 连接池：`pool_size=10, max_overflow=10, pool_recycle=1800`（PG 默认 100 连接上限，部门级够用且留余量）。
2. 进程内 TTL 缓存（`cachetools.TTLCache`，60 秒）+ 显式失效钩子挂在组织/流程/策略的写操作上。**不引 Redis**——单人维护多一个组件就是多一个故障源。
3. 失效策略必须与已有的一致性模型对齐：P1-1 合并后，组织变更走 `_bump(revoke)` 的地方同步清缓存。

**预期收益**：待办页每次请求省 3-5 次组织/流程查询，DB CPU 明显下降；策略读取从毫秒级降到内存级。
**工作量**：1-2 天。**注意**：缓存失效写错会造成权限越权，必须挂在写路径事务提交后。

---

### P1-4　API 版本化留出升级通道

**证据**：196 个接口全部挂在 `/api` 前缀下（`_settings.api_prefix`），无版本段。智能体层、前端、外部集成都直连同一套路径。

**做法**：新增 `/api/v1` 别名（`include_router(..., prefix=f"{api_prefix}/v1")` 与旧前缀并存一段时间），前端与智能体层切 v1，旧前缀保留两个版本周期后下线。

**预期收益**：未来做破坏性字段变更时可以灰度，不用"改一处全链路一起动"。这是扩展性的最低成本保险。
**工作量**：1 天（改注册 + 改前端 baseURL + 回归）。

---

### P1-5　AI 质量评测集扩容

**证据**：已有 `tests/evaluation` 目录与"36 样本 / 39 项通过"的合成评测，但样本量太小，无法支撑阈值调优（`INTENT_CONFIDENCE_THRESHOLD=0.6`、`FAQ_ANSWER_THRESHOLD=0.65` 都是拍出来的）。

**做法**：
1. 把评测集扩到 150-200 条，覆盖：应路由 / 应拒绝（五类 dedicated_workbench 场景）/ 边界模糊 / 带错别字 / 多意图。
2. 输出混淆矩阵，而不是单一通过率——重点看"该拒绝却被放行"的假阴性，这是安全相关的。
3. 阈值调整必须跑一遍评测集再定，把结果记进 `docs/`。

**预期收益**：意图分类的误判率从"不知道"变成"有数"；阈值调整有依据，不会调一次好一次坏。
**工作量**：2-3 天（造样本比跑评测费时）。

## 四、P2：季度内做，打磨与加固

### P2-1　安全响应头与 CORS 收敛

**证据**：`app/main.py` 只注册了 Trace / Auth / CORS 三个中间件，无 `X-Content-Type-Options`、`X-Frame-Options`、`Referrer-Policy`、`CSP`；且非 builtin 模式下 `allow_origins=['*']`。

**做法**：
1. 加安全响应头中间件。CSP 要放宽 `connect-src`/`media-src` 给 TRTC 域名，否则会议功能会被拦——这条必须在会议页实测。
2. `AUTH_PROVIDER != builtin` 时若 `AUTH_ALLOWED_ORIGINS` 未显式配置，**启动直接失败**而不是退化成 `*`。fail-closed 比"能跑起来"重要。

**收益**：防点击劫持、防 MIME 嗅探；跨域配置不会因为一次环境变量遗漏而放开。
**工作量**：半天。

### P2-2　依赖漏洞扫描进流程

**证据**：无任何依赖审计环节；`requirements.txt` 24 项 + npm 依赖含 Tencent 云 SDK 多个包。

**做法**：`pip-audit` + `npm audit --omit=dev` 挂进 P0-4 的 CI，只对 high/critical 报警，不阻塞低危。

**收益**：安全公告出来后能在一天内知道影响面，而不是等出事。

### P2-3　前端类型从 OpenAPI 生成

**证据**：119 处 `any`/`as any`，0 处 `@ts-ignore`（说明没在硬压类型，是确实没定义）。

**做法**：用 `openapi-typescript` 从 `http://127.0.0.1:8015/openapi.json` 生成 `src/types/api.d.ts`，逐步替换手写接口类型。优先后端契约稳定的模块（组织、请假、审批），AI 相关响应结构易变，可保留 `any`。

**收益**：后端字段改名时编译期就报错，而不是运行时白屏。119 处不必一次清完，按模块推进。

### P2-4　可观测性补一层指标出口

**证据**：已有 31 处计时埋点、`ops/operations_monitor.py`（健康检查 + 积压/备份告警 + 独立看门狗），但指标没有统一出口，只能看日志。

**做法**：加 `/metrics`（Prometheus 文本格式，`prometheus_client` 一个依赖即可），暴露：请求量/延迟分位、LLM 调用次数与 token 用量、出箱积压深度、降级状态。配一个 Grafana 面板或直接用 `curl` + 简单脚本。

**收益**：从"出问题看日志排查"变成"看板提前发现"。部门级试点的可用性承诺（≥99%）需要这个才能自证。

### P2-5　超长函数拆解

**证据**：>80 行函数 10 个，最长 `thread_service._send_message` 141 行、`interrupt_service._resume_locked` 138 行、`tools/base.py:call_tool` 118 行。

**做法**：只拆这三个（其余 80-100 行的可接受）。`_send_message` 按"取上下文 / 调模型 / 落库 / 出事件"切四段；`_resume_locked` 按中断类型分派。拆的时候不改逻辑，纯提取函数 + 现有测试兜底。

**收益**：这三处是对话与中断恢复的核心，改动频率高，可读性收益直接。

## 六、执行顺序建议

**第一周**（P0 全套）：P0-1 主包 → P0-4 覆盖率基线 → P0-3 慢查询。先做 P0-1，因为它是唯一"用户能立刻感知"的改动，也是投入最小、观感最强的。

**第二至三周**：P0-2 分页 + P1-2 依赖 lock。分页依赖 P0-3 的索引结论，别提前开。

**第四至六周**：P1-1 服务层收敛（此时覆盖率已就位，敢动手）+ P1-4 版本化。

**试点上线前必做**：P2-1 安全响应头、P2-2 漏洞扫描、P2-4 指标出口——这三项是"部门级可用性承诺"的支撑，缺了就只能口头保证。

**可延后到 V2**：P2-3 类型生成、P2-5 函数拆解，属于长期健康度投入，不影响试点。

## 七、不建议做的事（同样重要）

| 不建议 | 原因 |
|---|---|
| 引入 Redis / 消息队列 | 部门级 5-10 人，进程内 TTL + 现有出箱表已足够；多一个组件就是多一个凌晨要修的东西 |
