# 四大核心模块业务功能实现流程说明

> 说明口径：以下四段均按源码实际调用链撰写，涉及的对象名、状态枚举、校验顺序、锁与事务边界均可在 `backend/app/services/` 与 `backend/app/models/` 中逐一对应。

---

## 一、办公业务模块

办公业务模块承担系统的法定执行面职责，目标是把请假、报销、工单三类高频事项从口头请示与线下流转，转变为具备唯一业务编号、完整状态机与不可抵赖留痕的正式记录，因此它的验收标准不是"页面能提交"，而是"任何一笔单据都能回答谁在什么时间、基于哪一版规则、做了什么决定"。该模块的关键对象分三层：配置层是 `OAWorkflowDefinition` 与 `OAWorkflowVersion`（后者携带 `form_version`、`rule_version` 以及 workflow/form/rule 三个哈希，供事后证明"这单按的是哪版规则"）；实例层是 `OAWorkflowInstance`、`OAWorkflowNode` 与 `OAWorkflowSeat`（席位同时记录 `original_user_id` 与 `effective_user_id`，并带 `substituted`、`escalated` 标记，使代批与超时升级可追溯）；单据层是 `OALeave`/`OALeaveVersion` 与 `OAReimbursement`/`OAReimbursementVersion` 成对的"当前态 + 版本快照"结构，另配 `OABalance` 额度账、`OAApprovalDelegation` 委托关系，以及 `OAWorkflowOperation`、`OAWorkflowEvent`、`OAWorkflowOutbox` 三张台账分别承载命令幂等、事件溯源与通知出箱。输入是申请人填写的表单字段、附件清单、客户端持有的 `expected_revision` 与 `submission_version`，以及必填的 `operation_id`；输出是流转后的单据状态、下一处理人待办、通知出箱记录和一条可回放的审计事件。处理步骤严格按以下顺序执行：先做归属与写权限校验，并把附件预检（上传、扫描、清单核对）刻意放在串行事务之外，以隔离文件 IO 与扫描延迟；随后进入统一命令通道，依次取得租户锁与申请人维度的咨询锁、校验乐观锁版本、按 `operation_id` 查幂等台账（同键不同内容直接以 409 拒绝），再在保存点内执行领域逻辑——读取当前已发布的流程版本、校验字段是否符合该版本的表单定义、检查假种或费用类别是否强制附件、检测与审批中或已通过单据的日期重叠，之后由 `resolve_route` 从入口节点遍历流程图：分支节点用 `evaluate_condition` 做确定性求值（金额以 `amount_minor` 整数比较、日期先转 `date` 再比较，全程不经过模型），审批节点按 selector 解析席位并逐个校验在职状态、权限与自审冲突，任何异常都写入 `pause_reasons` 让实例以 `PAUSED` 落库而不是带病流转；路由确定后写单据版本快照（含字段差异 `differences` 便于追责）、创建实例并把 `route_snapshot` 一并冻结，节点与席位以 `PENDING` 落库，激活首节点、预占额度（RESERVE），最后在同一事务内写入操作台账、事件与逐接收人鉴权过的通知出箱。审批侧由 `decide` 承接，重新加锁重读后依次校验修正字段白名单、节点轮次与席位状态、未对账写入（存在对账异常时禁止办理）、全部待办席位资格是否仍有效（人员变动需管理员介入），非本人办理时再校验委托关系；驳回则终止剩余节点并释放额度，通过则按单签、或签、会签规则推进，末节点通过后置 `APPROVED` 并核销额度。与其他模块的边界是：本模块向工作台输出只读待办投影，向通知子系统输出出箱事件，额度与委托在本地闭环；智能与知识模块只能读取单据、额度与路由结果生成预检建议，任何写动作必须回到本模块的命令通道，因此"智能体不能改状态"是结构性约束而非口头约定。技术栈在此的作用是硬约束：PostgreSQL 的 CheckConstraint 把实例状态锁在 `IN_REVIEW / PAUSED / APPROVED / REJECTED / CANCELLED` 五种合法值内，租户复合唯一键与复合外键保证跨租户不可见，SQLAlchemy 的 `begin_nested` 保存点让领域异常不污染外层事务，`pg_advisory_xact_lock` 串行化同一申请人的并发提交，FastAPI 依赖注入统一挂载鉴权，Pydantic 在入口完成字段与类型校验，Alembic 保证结构演进可重放，审计与业务同事务提交使"业务成功而审计丢失"在架构上不可能发生。

## 二、协同办公模块

协同办公模块的目标不是"增加几个功能页"，而是为会议、文档、邮件、业务任务与公告建立统一的协作产物治理规则：所有由人或智能体产生的内容先落草稿、经人工确认后才成为正式记录，避免生成式内容直接进入企业事实层。其关键对象按业务线分布：会议线是 `OAMeeting` 与 `OAMeetingAttendee`，状态机限定为 `DRAFT / SCHEDULED / IN_PROGRESS / ENDED / CANCELLED`，配套 `meeting_transcription` 与 `meeting_segment` 承载转写原文与分段；文档线是 `document_record` 与 `document_draft_version`；邮件线是 `email_record` 与 `email_draft_version`，公共邮箱另有独立收发通道；任务线是 `work_task_batch`、`work_task` 与 `work_task_event`；公告线是 `oa_announcement`。输入分别是会议邀约（时间、参会人、议题与主持人）、会议音频流、文档模板与素材、原始邮件正文与附件、以及业务任务所依赖的来源快照；输出是会议状态与纪要版本、文档正式版本、邮件发送留痕、可指派的任务与对应待办。处理步骤以会议为主线最具代表性：先由 `options` 与 `members` 解析可选参会人与会议室资源，`save` 以乐观锁创建或修改 `DRAFT`，`conflicts` 在提交前做时间冲突检测，`transition` 按 `publish / start / end / cancel` 推进并复用统一命令通道，其中保存、发布、取消、重试仅组织者可为，开始与结束限组织者或主持人，纪要编辑与确认另按 `editor` 判定；会议结束后，转写服务经带密钥校验的回调把音频文本写入转写表并分段，`meeting_graph` 据此生成纪要草稿，`attach_minutes` 挂接草稿、`notify_minutes_confirmed` 在确认后触发通知；每次 `execute` 结束后会在同一事务内把本命令产生的出箱记录物化为站内信（`dispatch`），而外部传输（邮件、企微群机器人）交由独立 worker 异步完成，保证"通知要发"与"通知已发"解耦。文档与邮件走同构的草稿版本流程：入口校验模板或来源可见性，生成结果先落 `*_draft_version`，`_reviewable` 与 `_validated_draft` 判定是否可审核，人工确认后才写入正式记录，文档来源与知识库来源共用一套可见性判定（`_knowledge_scope`、`_source_access`），因此"文档能不能被检索"与"谁能看这份文档"是同一套规则。任务线则先 `create_batch` 冻结 `source_snapshot`，再由 `work_task_graph` 抽取候选（外层用 25 秒超时保护，防止智能环节拖死请求），候选经人工确认后才指派为正式任务并写入事件与通知。模块间关系上：本模块向工作台输出任务与待办，向通知子系统输出出箱事件，向智能与知识模块提供文档与会议文本作为知识来源，同时接收来自工单、审批等业务对象的来源引用以生成任务。技术栈的具体作用体现在四处：`graph/meeting_graph.py` 与 `graph/work_task_graph.py` 由业务服务直接调用而不经过 SuperAgent 路由，从入口上杜绝"一句话误建会议或任务"；腾讯云 TRTC SDK 在服务端签发有时效的 UserSig，密钥不出服务端，前端 RoomKit 组件只消费凭证；转写回调以密钥校验加异步投递的方式接入，避免长音频阻塞请求线程；出箱表加独立 worker 的组合把外部通道故障隔离在通知层，httpx 的超时配置保证外部依赖不会反向拖垮业务事务。

## 三、智能与知识模块

智能与知识模块的职责是把理解、检索与生成能力封装为可约束、可审计、可降级的服务，其产出被严格定义为"建议"而非"事实"，因此模块内部不存在任何直接修改业务状态的路径。关键对象包括会话域的 `AgentThread` 与 `AgentMessage`、人工介入域的 `human_decision` 与 `handoff_snapshot`、兜底域的 `human_queue_item`、知识域的 `knowledge_document`、`knowledge_chunk`、`knowledge_version` 与 `knowledge_source`、合同域的 `contract_record`、`contract_review_version` 与 `contract_source`，以及贯穿质量与成本的 `precheck_result`、`model_usage` 与 `runtime_span`。输入有三类：用户自然语言问题、上传的文档或合同原件、以及经授权读取的业务上下文（用户身份、假期额度、路由结果、单据摘要）；输出则是带来源标注的回答、结构化的草稿、条款风险意见、预检结论与任务候选。处理流程按能力分为四条链路。对话链路从 `AgentThread` 建立会话标识开始，SuperAgent 在 `START` 处先做场景分流：`work_task / report / contract / document / email` 五类高风险场景直接进入 `dedicated_workbench` 并返回"请通过对应业务工作台执行命令"，会议场景走会议子图与纪要复核节点，其余才进入 `load_context → classify_intent → leave / faq / ticket` 的主路径；`load_context` 同时读取降级开关，命中即转入 `degrade` 分支终止，正常路径下每个节点只能调用 `SCENE_TOOLS` 为该场景声明的工具，命中 `WRITE_TOOLS` 的写工具必须经人工介入（interrupt）确认并携带幂等键，末尾统一由 `audit_tail` 落审计。知识链路分导入与检索两段：导入时对正文取 SHA-256 内容指纹，按段落与句单元切分为 chunk，经 Embedding 抽象批量向量化后连同 `source_location`（形如"标题#chunk-n"）一并入库；检索时先 `require_fresh_identity` 重查身份并校验 `knowledge:read` 权限，再把可见范围收窄为 `permission_tags = actor.depts` 实现部门级隔离，优先走版本化切片检索，且在自研本体模式下若当前版本无命中则直接返回空集，绝不回落到缺少租户归属的旧切片——这一条是防止越权泄露的关键。合同链路由四个显式节点组成：`extract_clauses` 抽取条款、`check_rules` 执行确定性规则并冻结 `rule_snapshot`、`analyze_risks` 仅在正文超过 8000 字符时才调用 DeepAgents 做计划与分块分析（否则走确定性引擎，模型调用次数为零）、`summarize` 汇总并明确标注"此结果无法律批准效力"，最终只有通过服务层校验的状态才被持久化为审查版本。报表链路则把指标注册化（`METRICS` 定义指标口径、来源表与时间字段），查询在独立只读事务中执行，查询计划需人工审批，结果以不可变版本加哈希留存。与其他模块的关系清晰且单向：本模块只读办公业务的单据、额度与路由，生成的文档、邮件、会议纪要草稿交由协同办公模块定稿，FAQ 未命中或置信度不足时移交客服队列由人处理，全部调用与决策写审计供系统管理模块追查。技术栈的作用可逐项对应：LangGraph 的状态图让"哪些场景允许自由对话、哪些必须走工作台"成为图结构上的硬分支，Checkpointer 以 thread 为单位持久化状态使长任务可断点续跑；DeepAgents 承担超长文本的计划与分块，配合工具白名单与调用预算约束其行为边界；pgvector 的 HNSW 索引在单库内完成向量检索，使知识切片与业务数据共享同一套事务、备份与权限体系；LangChain Core 的模型抽象让主备模型切换只改配置；Pydantic 在工具入口完成入参校验，把模型输出的不确定性挡在业务逻辑之外。

## 四、系统管理模块

系统管理模块的目标是让整套系统"可配置、可审计、可观测、可回退"，并且把配置与权限变更本身也当作受控业务来管理——因为在这类系统里，改一条流程规则或收回一个角色的破坏力，往往大于提交一张单据。其关键对象分为五组：组织与权限组是 `OAUser`、`OAMembership`、`OARole`、`OAUserRole`、`OAPosition`、`OADepartment` 与权限集合；流程配置组是 `OAWorkflowDefinition` 及其 `OAWorkflowVersion`；策略组是 `policy_version`、`agent_policy` 与 `oa_ai_scope`；审计与治理组是 `audit_event`、`audit_export`、`degradation_state`、`operational_errors`、`runtime_span` 与 `model_usage`；幂等与一致性组是 `idempotency_record` 与操作台账。输入是管理员的结构化操作（建部门、设岗位、建用户、分配角色、调整流程定义、设定策略阈值、下发降级指令、发起审计导出），输出是即时生效的配置版本、被收回的授权、可导出的脱敏审计证据链、降级状态与运行告警。处理路径按能力分为五条。组织与权限路径先由 `overview` 汇总组织树与人员分布，`save_department` 与 `save_position` 在租户维度内维护层级与唯一性，`create_user` 与 `_assign` 完成用户建档和角色权限绑定，任何用户状态或角色变更都会触发 `_bump(revoke=True)` 让旧授权立即失效；配合 `authorization_service` 中"每个新业务动作都重新解析身份"的 `require_fresh_identity`，实现降职、离岗后旧令牌不再具备审批能力。流程配置路径采用草稿与发布分离：`save_definition` 只更新草稿并递增 revision，`validate_definition` 校验节点、条件与表单定义的结构合法性，`publish_definition` 才生成不可变的 `OAWorkflowVersion` 并写入三个哈希、递增 `published_version`；由于实例在创建时已把 `route_snapshot` 冻结，后续任何配置修改都不会影响在途单据，只会作用于新提交的单据。策略路径以 `policy_version` 承载版本化的场景开关与阈值（`is_scene_enabled`、`get_thresholds`），`agent_policy` 与 `oa_ai_scope` 限定智能体在哪些部门、哪些场景、哪些动作上可用，从而把"智能能力开放到什么程度"变成可审计的配置项。审计路径由 `audit_service` 统一收口，从 `contextvars` 自动读取 trace_id、操作者与策略版本，覆盖会话、路由、工具调用、预检、检索、回答、人工决定、写入、通知、重试、异常、配置变更与降级等事件；`audit_export_service` 负责生成受控且脱敏的导出件并留哈希，`oa_audit_access` 控制谁能看哪一段证据。降级与观测路径由 `degradation_service` 与 `ops` 承担：降级状态支持 global、按场景、按范围三档，并区分 `new_task_action` 与 `inflight_action`，使"新单转人工、在途单照常跑完"成为可执行的语义而不是模糊的开关；`operations_monitor` 以独立数据库连接和独立状态存储运行看门狗，检查应用、数据库与通知积压，即使主应用或数据库不可用仍能记录与告警；`runtime_span` 采集链路耗时，`readiness` 提供就绪探针并在依赖不可用时按 fail-closed 原则拒绝放行。与其他模块的关系是"横向供能"：本模块为办公业务下发已发布的流程版本与权限判定，为智能与知识模块下发场景开关与降级指令，为全部模块提供审计收口与告警出口。技术栈在此承担的是基础设施级保障：PostgreSQL 的租户复合唯一键与复合外键（`tenant_key` / `tenant_fk`）在数据库层阻断跨租户数据串用，CheckConstraint 把状态与版本号约束在合法区间，Alembic 让每一次结构演进可重放可回滚，Pydantic 保证流程定义与策略入参在入库前结构合法，PyJWT 与 argon2 构成认证底座且 Secure Cookie、CORS 白名单等参数全部配置化，`contextvars` 让 trace_id 与操作者身份贯穿异步调用链而无需逐层传参，独立连接的超时监控与 Docker 健康检查共同保证"系统知道自己在什么状态下"。

## 附：四模块的协作主线

四段流程合起来是一条完整闭环：**系统管理**定义规则与授权 → **办公业务**在规则内产生法定记录 → **协同办公**沉淀协作产物并驱动通知 → **智能与知识**在只读上下文上生成建议、并把建议交回人工确认。四者共享同一套身份、审计、幂等与通知基础设施，任何一处写入都落在 `OAWorkflowOperation` 台账与 `audit_event` 之上，因此"跨模块可追溯"不是靠人对齐，而是靠统一命令通道在结构上保证。
