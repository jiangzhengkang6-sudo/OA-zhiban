# 核心功能模块分析（基于源码实测）

> 判断依据：`backend/app/main.py` 的路由注册（35 个 router）、`backend/app/services/`（78 个服务模块）、`backend/app/graph/`（7 个子图 + SuperAgent）、`backend/app/models/`（61 个数据模型）、`frontend/src/navigation.ts`（6 组导航）+ `frontend/src/views/`（40 个页面）。以下模块划分不是按 PRD 抄的，是按代码实际组织方式归纳的。

---

## 一、模块总览

系统实际是**六层结构**：最上面是 6 个业务域（与前端导航一一对应），下面压着 5 层横切支撑。

```
┌──────────────────────────────────────────────────────────────┐
│  业务域（用户可见，对应前端 6 组导航 / 40 个页面）              │
│  ① 工作台  ② 办公业务  ③ 协同办公  ④ 智能与知识  ⑤ 数据报表  ⑥ 系统管理 │
├──────────────────────────────────────────────────────────────┤
│  智能编排层    SuperAgent + 7 个子图 + 工具白名单              │
├──────────────────────────────────────────────────────────────┤
│  确定性执行业务层  请假/报销/审批链/工单/额度/委托/公告/会议    │
│                    （统一走 OACommand 命令通道）               │
├──────────────────────────────────────────────────────────────┤
│  基础能力层    身份认证 · RBAC · 幂等 · 审计 · 降级 · 通知投递  │
├──────────────────────────────────────────────────────────────┤
│  集成适配层    Mock / Builtin / Real 三套 Provider + 三套外部通道│
├──────────────────────────────────────────────────────────────┤
│  数据与运维层  PostgreSQL 单库 · 迁移 · 备份恢复 · 监控告警     │
└──────────────────────────────────────────────────────────────┘
```

## 二、六个业务域（用户可见的功能模块）

### ① 工作台（统一入口）

**职责**：所有身份的人登录后第一屏——我的任务 + 通知与站内信。

| 项 | 内容 |
|---|---|
| 后端实现 | `services/oa_work_item_service.py`（统一待办**只读投影**）、`oa_notification_service.py`、`oa_notification_worker.py`、`oa_wecom_worker.py`、`oa_notification_source.py` |
| 前端页面 | `TaskCenterView.vue`、`NotificationWorkbenchView.vue` |
| 路由 | `/oa/work-items`、`/oa/notifications` |

**设计要点（源码里很明确）**：统一待办是**只读投影**，模块 docstring 写着 "Read-only pending projection. Decisions stay in their original domain services."——待办列表只负责聚合展示（审批待办 + 业务任务），真正的决策动作必须回到各自领域服务里执行，不允许在工作台直接改状态。这是防止"绕过审批链改状态"的关键设计。

**通知投递**是独立的一套可靠投递机制：`claim/commit before external IO`、`finish only the current attempt token`、按物理群合并批次（OAWecomBatch），说明它不是"发个 HTTP 就完事"，而是有认领、令牌、重试、批次去重的持久化投递队列。

### ② 办公业务（OA 本体核心，项目最重的模块）

**职责**：真正产生"法定记录"的部分——申请、审批、工单、额度。

| 子模块 | 后端实现 | 前端页面 |
|---|---|---|
| 我的申请（请假） | `oa_leave_service.py`、`leave_application_service.py`、`leave_attachment_service.py` | `OALeavesView.vue`、`LeaveFormView.vue`、`LeaveDetailView.vue` |
| 报销工作台 | `oa_reimbursement_service.py`、`oa_reimbursement_attachment_service.py` | `ReimbursementWorkbenchView.vue` |
| 审批工作台 | `oa_approval_service.py`（**当前席位鉴权 + 确定性决策**）、`oa_workflow_subject.py` | `OAApprovalsView.vue`、`ApprovalInboxView.vue` |
| 审批委托 | `oa_delegation_service.py`（显式、不可传递、每次使用都重新校验身份） | `OADelegationsView.vue` |
| 请假额度 | `oa_balance_service.py` | `OABalancesView.vue` |
| 工单工作台 | `oa_ticket_service.py`、`ticket_service.py`、`ticket_draft_service.py`、`ticket_assignment_rule.py`（模型） | `TicketWorkbenchView.vue`、`TicketFormalWorkbenchView.vue`、`TicketDetailView.vue` |
| 客服队列（人工兜底） | `support_queue_service.py`、`handoff_service.py`、`member_handoff_service.py` | `SupportQueueView.vue`、`SupportWorkItemView.vue` |

**这个域的核心是审批链引擎**，代码在 `oa_workflow_service.py` + `oa_workflow` 模型族：

- `OAWorkflowDefinition`（草稿 + revision）→ `OAWorkflowVersion`（发布版本，含 `form_version`/`rule_version`/三个 hash）→ `OAWorkflowNode` / `OAWorkflowSeat`（节点与席位）→ `OAWorkflowInstance`（实例，`route_snapshot` 快照路由）
- 关键机制：**发布即冻结**。实例创建时把路由快照存进 `route_snapshot`，后续流程配置改了不影响在途单据——这是审批系统最基本的正确性要求
- 条件路由由 `evaluate_condition` 确定性执行（eq/ne/lt/le/gt/ge/in），金额按 `amount_minor` 分为单位比较，日期转 date 后比较——**路由判断不经过 LLM**
- 实例状态受数据库 CheckConstraint 约束：`IN_REVIEW / PAUSED / APPROVED / REJECTED / CANCELLED`，非法状态写不进去

**委托的约束设计**值得单独说：`Explicit, non-transitive delegation; evaluate current identity on every use`——委托不可链式传递，每次代批都重新校验委托人当前身份，防止"授权一次永久生效"的安全漏洞。

### ④ 智能与知识

| 子模块 | 后端实现 | 前端页面 |
|---|---|---|
| 智能助手（对话） | `graph/superagent.py`、`graph/*_graph.py`、`thread_service.py`、`interrupt_service.py` | `AssistantView.vue` |
| 知识库（RAG） | `knowledge_service.py`（切分+向量化+检索）、`knowledge_reader_service.py`、`knowledge_version_service.py` | `KnowledgeView.vue`、`KnowledgeReaderView.vue` |
| 合同审查 | `contract_service.py`、`contract_deepagents.py`、`contract_parser.py`、`contract_rules.py` | `ContractView.vue` |
| 来源治理 | `knowledge_source.py` / `oa_notification_source.py` 等 | `KnowledgeSourceView.vue` |

**SuperAgent 的真实路由结构**（读源码得来，和"9 个智能体全部由 SuperAgent 统一调度"的说法有出入，这里给准确版）：

```
START
 ├─ scene ∈ {work_task, report, contract, document, email} → dedicated_workbench（直接 END，返回"请通过对应业务工作台执行命令"）
 ├─ scene == meeting → meeting 子图 → meeting_review（要不要生成纪要）
 └─ 其余 → load_context → [降级?] → classify_intent → leave / faq / ticket → audit_tail → END
```

也就是说：**SuperAgent 只路由 leave / faq / ticket / meeting 四个子图**（外加 meeting_review 节点）；其余五个场景（合同、报表、任务、文档、邮件）**被显式挡住**，必须从各自工作台发起。源码注释写得很直白：

> "The selected workflow is authoritative; classification cannot silently turn a knowledge question into a ticket creation request."

这是一个**有意为之的安全设计**：意图分类可能出错，如果允许"一句话创建合同/发起报表"，误判就会产生错误业务动作。所以高风险场景不允许走自由对话入口。

**工具白名单是硬边界**（`tools/registry.py` 的 `SCENE_TOOLS`）：每个场景只能调用自己那几个工具，比如 leave 只能调 `get_user_context / get_leave_balance / validate_leave_form / get_approval_route / create_or_update_oa_approval / notify_user`；`WRITE_TOOLS` 单独标注，写工具必须过 HITL + 幂等键。

### ⑤ 数据报表

| 项 | 内容 |
|---|---|
| 后端 | `report_service.py`、`report_query.py`、`report_metrics.py`、`report_generator.py` |
| 前端 | `ReportView.vue` |
| 路由 | `GET /metrics`、`POST ""`、`GET /{id}`、`GET /{id}/versions`、`POST /{id}/approve-plan`、`POST /{id}/retry`、`POST /{id}/publish` |

**这是全项目设计最"学术"的一个模块**，三个约束很有意思：

1. **不让 LLM 自由写 SQL**。指标是**注册制**（`report_metrics.py` 里的 `METRICS` 字典，每个指标带 `metric_id / version / definition / source / time_field`），查询只能跑注册过的 SELECT，且"Registry-only SELECTs in a separate PostgreSQL read-only transaction"——单独开只读事务执行
2. **查询计划要人工审批**（`approve-plan` 路由）——智能体只能提计划，人批准才能执行
3. **结果是不可变证据**（`ReportRecord` + `ReportVersion`），带 hash 和 trace_id，可追溯到哪次查询、哪个指标版本

异常检测也是规则化的：`relative_change`、阈值 50%、"仅前期非零时计算变化率"，并明确写"原因未证实"——不编造归因。

| 子模块 | 后端实现 | 前端页面 |

| 策略版本 | `policy_service.py`、`policy_version_service.py` | `PolicyVersionView.vue` |
| 审计中心 | `audit_service.py`、`audit_export_service.py`、`oa_audit_access.py` | `AuditView.vue` |

| 降级控制 | `degradation_service.py` | `DegradationView.vue` |

**降级控制**是这套系统的特色能力：`DegradationState` 支持 global / 按场景 / 按范围三档，且区分 `new_task_action`（新任务怎么处理）和 `inflight_action`（在途任务怎么处理）——降级不是简单关开关，而是"新单转人工、在途单继续跑完"这种细粒度语义。

**审计**覆盖事件极广，docstring 列了：会话/路由/工具/预检/检索/回答/人工决定/写入/通知/重试/异常/配置/降级。审计从 contextvars 自动取 trace_id / actor / policy_version，业务代码不用手动传参。

**运维监控是独立看门狗**："Independent, tenant-bound watchdog. State survives database/application outages."——监控自己不能依赖被监控的系统，这是运维模块的正确做法（用独立连接、独立存储）。

## 三、五个横切支撑层（不在导航里，但撑起全部业务）

### A. 身份与权限

| 文件 | 职责 |
|---|---|
| `middleware/auth.py` | 登录态解析，挂载 `request.state` 与 contextvars |
| `middleware/trace.py` | trace_id 贯穿全链路 |
| `services/identity_service.py` | 用户/成员/角色/职位/部门，`current_identity`、`lock_tenant` |
| `services/authorization_service.py` | **Deny-by-default** 资源与工具决策，`require_fresh_identity`（不信 JWT 里的旧角色快照） |
| `services/oa_access_service.py` | OA 域内鉴权：`authorize_oa`、`OAAccessTarget`、`builtin_actor`、数据范围 |
| `services/oa_scope_service.py` | 数据可见范围（本人/本部门/跨部门） |

**两个安全细节**：① 默认拒绝（deny-by-default），没显式授权的就是不行；② "Never trust a stale graph/JWT role snapshot for a new business action"——每个新业务动作都重新查一次身份，防止"降职后旧 token 还能批"。

### B. 确定性执行内核

| 文件 | 职责 |
|---|---|
| `services/oa_command_service.py` | **所有写操作的唯一入口**：`OACommand`（kind/target_id/target_version/operation_id/payload）+ `canonical_hash` + 乐观锁版本号 |
| `services/oa_workflow_service.py` | 流程定义编译、条件求值、路由快照 |
| `services/oa_approval_service.py` | 当前席位鉴权、确定性决策 |
| `services/idempotency_service.py` | **先提交认领事务、再做外部副作用、最后二次事务完成**；pending/unknown 状态绝不重试直到外部系统对账 |
| `services/oa_workflow_subject.py` | 实例主体解析（请假单 / 报销单） |
| `services/oa_workflow_scheduler.py` | 超时升级调度 |

这段是项目的工程核心。`oa_command_service` 的 docstring 一句话说清了纪律："Serialized, idempotent, atomic business commands. Callers own final commit."；`idempotency_service` 更狠："Callers MUST commit the claim transaction BEFORE external side effects, then complete in a second transaction."

## 四、几个从代码里读出来的关键结论

**1. 系统是"双轨制"并且已完成主力迁移**
`models/` 里同时存在 `oa_*` 族（自研本体）和 `approval_instance`/`ticket_record` 族（P1-P3 演示期）。前端 `navigation.ts` 里有一行关键代码：

```ts
const mockOnly = new Set(['/leaves', '/approvals', '/ticket', '/support'])
// builtin 模式下这些入口被隐藏
```

意思是：切到自研本体（`AUTH_PROVIDER=builtin`）后，旧的 mock 演示页面自动从导航消失，只留新本体的页面。**说明"从辅助底座升级为正式 OA"这件事，代码层面已经完成了主体工程**，旧链路保留仅为兼容与回归。

**2. 智能层被刻意"关在笼子里"**
三层约束叠加：场景白名单（`SCENE_TOOLS`）→ 写工具单独标记（`WRITE_TOOLS` 必须 HITL + 幂等）→ 高风险场景拒绝自由对话入口（`dedicated_workbench`）。加上降级开关和"智能全下线仍可纯人工跑"，智能层是**可插拔的增强，不是业务单点**。

**3. 确定性判断与概率性判断严格分离**
审批路由、额度扣减、金额比较、指标计算全部是代码（`evaluate_condition`、`report_metrics`、`amount_minor` 整数比较）；LLM 只做预检意见、摘要、问答、草稿。这条线在代码里划得非常干净，是整个系统敢落地的前提。

**4. 可靠性是靠"顺序"保证的，不是靠重试**
幂等 = 先提交认领 → 再做外部副作用 → 再二次事务完成；通知 = 先 claim 再发、只 finish 当前 attempt token；审批 = 实例创建即冻结路由快照。这些顺序约束写在 docstring 里，是可被面试追问的工程细节。
